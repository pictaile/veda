## S1 — семплер бачить лише логіти

```cpp
class Sampler {
    virtual int32_t sample(const core::Tensor& logits) = 0;   // [V] або [1,V] → id
};
```

Не модель, не промпт, не токенізатор. Ця вузькість і є те, що §7 архітектури називає одним із трьох,
чого Фаза 1 не має закрити: обмежене декодування («видавай лише токени, що зберігають JSON валідним»)
стає **предикатом над тензором логітів**, а не перепроєктуванням.

**Greedy — це argmax, і softmax йому не потрібен.** Перевірено на 50 випадкових наборах: argmax
логітів і argmax після softmax дають той самий id, бо softmax монотонний. Нормалізація витратила б
151 936 експонент на токен, щоб не змінити відповіді — тому LM-head у E10 навмисно не нормалізує.

Три деталі, які легко проґавити:

| Рішення | Причина |
|---|---|
| нічия → **нижчий id** | без явного правила дві реалізації розійдуться на нічиїй і дадуть різний текст |
| NaN **кидає** | будь-яке порівняння з NaN хибне, тож наївний argmax тихо поверне індекс 0 |
| `sample` неконстантний | у greedy стану немає, але температурний і top-p несуть генератор — інтерфейс, реалізаціям якого потрібен `mutable`-хак, гірший |

## S2 — температура і два способи обрізання

**Температура — це ділення перед експонентою**, `softmax(logits / T)`. Порядок логітів вона не
змінює ніколи; змінює **проміжки**, а softmax проміжки експоненціює.

```
частка топ-токена, виміряно на 20 000 кидків:
   T = 0.3  →  0.93       майже greedy
   T = 1.0  →  0.64
   T = 5.0  →  0.36       наближається до рівномірного (0.25)
```

Це не «креативність», а **скільки власної невпевненості моделі шанувати**. `T = 0` приймається й
коротко замикається на argmax замість ділення на нуль.

### Чому top-p адаптується там, де top-k не може — виміряно

```
впевнена модель (p_top = 0.97):   top-p 0.9 → ядро з 1 токена
невпевнена (8 рівних):            top-p 0.9 → ядро з 7–8
той самий top-k = 1 на другій:     → 1 токен
```

Один і той самий `k` заширокий, коли модель певна, і завузький, коли ні — бо **k це кількість, а
впевненість ні**. Ядро top-p мале саме тоді, коли модель певна.

**Токен, що перетинає поріг, включається:** накопичена сума `0.644, 0.881, 0.968` при p = 0.9 дає
**три** id. Інакше набір давав би менше за p, а на впевненому розподілі був би порожній. **Ядро ніколи
не порожнє.**

### Чотири граничні тотожності — головний захист

```
TemperatureSampler(T = 0)  == GreedySampler
TopKSampler(k = 1)         == GreedySampler
TopPSampler(p → 0)         == GreedySampler
TopKSampler(k ≥ V)         == TemperatureSampler    id за id, той самий seed
```

Але тотожностей замало: вони не спіймають **пропущену ренормалізацію**. Тому тест малює 40 000 разів
і звіряє частоти з розподілом — і окремо для top-k, де ренормалізація змінює числа
(`[0.6439, 0.2369] / 0.8808 = [0.731, 0.269]`).

**Порядок:** температура **до** обрізання. Гарячіший семплер із тим самим `p` допускає ширше ядро —
обрізати спершу означало б обрізати інший набір.

**Детермінізм** — це вимога, а не зручність: той самий seed дає ту саму **послідовність** із 40 id,
інший seed — іншу. Без цього критерій прийняття епіку не перевірити ніяк.

## S3 — цикл генерації

```cpp
logits = head(transformer(ids));   next = sampler(logits);   ids.push_back(next);
```

**Автореґресія означає, що вихід стає входом.** Кожен крок обумовлюється всім сказаним, включно з
тим, що модель щойно сказала сама — тому помилка на кроці 3 формує кроки 4–50: модель не помиляється
щодо промпту, вона відповідає на промпт, який тепер містить її власну помилку.

### Ціна без кешу — ризик R3 у числах

Крок *n* проганяє трансформер по всіх `T+n` токенах, хоча `T+n−1` з них оброблялися ідентично
кроком раніше. Кожен шар перераховує всі ключі й значення для всіх попередніх позицій, а attention
потім викидає всі рядки оцінок, крім останнього.

```
промпт 25 токенів, 50 згенерованих:
  forward-проходів      50
  позиційних проходів   2 525        ← кожен префікс, щоразу
  із KV-кешем              75        (E12)
```

Перевірено арифметикою в тесті. Це очікувано, а не баг — і саме це прибирає E12.

### Дві умови зупинки, і обидві повідомляються

Ліміт токенів і EOS — **різні** результати: перше означає, що відповідь обрізана, друге — що модель
закінчила. Викликач, який їх не розрізняє, не може вирішити, чи продовжувати. **Стоп-токен не
віддається назовні** — він позначає кінець, і включення його поставило б `<|endoftext|>` у текст
користувача.

`forward_passes == generated.size()` — число, проти якого вимірюватиметься E12.

### Генератор не токенізує

Він знає модель і семплер, і більше нічого. Викликач приносить id і перетворює їх назад у текст.
Тому цикл тестується синтетичною моделлю **без токенізатора взагалі** — а щоб тест не залежав від
внутрішнього стану моделі, у ньому підлаштований **семплер**, а не голова.

## `veda_run` — тепер справжня генерація

```
$ ./build/veda_run <каталог> --prompt "Столиця України —" --max 32 --temp 0.7 --top-p 0.8 --seed 42
$ ./build/veda_run <каталог> --ids 5 12 40 --max 8

21 21 21 21 55 55 55 55

8 tokens in 12 ms  (666 tok/s)
8 forward passes, hit the limit
```

`--prompt` потребує `tokenizer.json` поруч із вагами; `--ids` працює без нього. Вивід іде через
`StreamingDecoder` з E5, тож **пів-символу ніколи не потрапляє в термінал**.

Порожній семплер за замовчуванням — greedy; `--temp` вмикає стохастичний, `--top-k`/`--top-p`
обрізання.

# E12 — KV-кеш

Стан: **епік E12 завершено** (сторі S1–S2, таски T1–T2).

## S1 — спершу виміряти

Крок *n* проганяє модель по всіх `T+n` токенах, і для кожної вже наявної позиції прихований стан
**ідентичний** учорашньому: той самий токен, та сама позиція, ті самі ваги, отже ті самі k і v.

```
позиційних проходів = N·T + N(N+1)/2

N      без кешу    із кешем    множник
 10        305          35        8.7
 50      2 525          75       33.7
200     25 100         225      111.6
```

Марна робота росте **квадратично**, корисна — лінійно.

**Q не кешується ніколи.** Запит ставиться один раз: запит позиції 5 дав вихід позиції 5 на тому
кроці, коли її згенерували, і жоден пізніший крок його не питає — пізніші кроки ставлять **свої**
запити проти **всіх** ключів. Ключі й значення читає кожна майбутня позиція; запити — ні, і ця
асиметрія і є весь дизайн.

**Що кеш не прибирає:** промпт усе одно треба обробити один раз. Цей прохід зветься *prefill*, він
неминучий, і саме тому довгий промпт коштує часу до першого токена.

## S2 — кеш

**Виділяється один раз на ліміт контексту**, не росте: ріст на кожному кроці означав би переалокацію
й копіювання всієї історії щотокена — та сама квадратичність, тільки в трафіку пам'яті.

**Валідний префікс — це зріз**, тобто в'ю без копіювання: другий робочий приклад із E1.S2.T7,
написаний за одинадцять епіків до того, як щось його потребувало.

### Три рішення, завдяки яким кешований шлях не потребував нової арифметики

| Рішення | Де ухвалене |
|---|---|
| причальна маска бере `T` і `S` **окремо**, дозволяючи `s ≤ S − T + t` | E8.S4.T5 |
| `attention_scores` дає ключам **власну довжину** | E7.S2.T3 |
| RoPE приймає `first_position` | E8.S2.T2 |

Жодне з них не змінилося. Це те, що купили попередні епіки.

### `advance` окремо від `append`

Усі шари дописують **за тим самим зсувом**; просування всередині `append` лишило б шар 1 на позицію
попереду шару 0. Наслідок, який виявився в тесті: `used()` під час кроку ще не враховує щойно
дописане, тому увага питає префікс **явної довжини** `first_position + new`. Нова позиція мусить
бачити себе — цього вимагає причальна маска.

### Головна перевірка — точна

```cpp
CHECK_EQ(plain.generated, quick.generated);   // токен у токен, не «близько»
```

Обидва шляхи роблять ту саму арифметику в тому самому порядку — усе інше було б багом, а не
округленням. Перевірено для чотирьох довжин промпту, для greedy й для стохастичного семплера з
фіксованим seed. Плюс окремо — що **приховані стани** збігаються, а не лише argmax.

**Некешований шлях лишається** й лишається протестованим: це еталон, проти якого судять кеш (критерій
прийняття роадмапу).

## Виміряно на синтетичній моделі

```
N=10:  без кешу  11 ms   із кешем  3 ms
N=20:            40 ms             6 ms
N=40:           172 ms            14 ms
N=80:           773 ms            32 ms       ← 24×
```

Прискорення **росте з довжиною**, як і має: марна робота квадратична. Виводи побайтово ідентичні.

`veda_run --no-cache` лишає старий шлях доступним із командного рядка.
