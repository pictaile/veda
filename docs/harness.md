# Reference Harness (епік E3) — що реалізовано

Документ описує `veda::testing` — інструмент, яким налагоджуватимуться всі наступні епіки. Стан:
**епік E3 завершено** (таски T1–T4; документи задач — у
`_bmad-output/planning-artifacts/roadmap/tasks/E3-*`).

Про шари нижче див. [`tensor.md`](tensor.md) і [`ops.md`](ops.md), про читання ваг — [`io.md`](io.md), про шари з вагами — [`nn.md`](nn.md), про увагу — [`attention.md`](attention.md), про токенізатор — [`tokenizer.md`](tokenizer.md), про генерацію — [`generate.md`](generate.md), про продуктивність — [`performance.md`](performance.md), про autograd — [`autograd.md`](autograd.md).

**Навіщо він іде перед кодом моделі.** Роадмап навмисно посунув цей епік уперед проти порядку
брифу. Причина в AD7: тести на порахованих вручну матрицях 2×2 ловлять помилки алгебри — і **не**
ловлять транспоновану вагу, переплутану розкладку голів чи хибну базу RoPE. Усе це рахується без
жодної помилки й повертає впевнену нісенітницю. Без цього епіку перша ознака проблеми — беззмістовний
текст у самому кінці.

**Головна ідея:** невдале порівняння мусить казати **де**. «Тензори різні» відправляє друкувати
масиви; «різні в (0, 3, 17), 17 із 512 елементів, знак перевернуто» — це гіпотеза, з якою можна
працювати. Повідомлення і є функцією, булеве значення тривіальне.

## T1 — допуски (Learn)

**Додавання fp32 не асоціативне.** З 24 бітами мантиси кожне додавання округлює:

```
(1e8 + −1e8) + 1.0  =  1.0
1e8 + (−1e8 + 1.0)  =  0.0     ← 1.0 округляється геть іще всередині дужок
```

Ті самі числа, той самий набір операцій, інший порядок — інша відповідь. Matmul підсумовує K
добутків; підсумувати їх в іншому порядку (інша вкладеність циклів, векторизована редукція, інший
BLAS) — математично те саме й чисельно інше. Veda й PyTorch не збігатимуться побітово, і не мають.

### Два доданки правила

```
|actual − expected| ≤ atol + rtol·|expected|
```

- **`atol`** рятує біля нуля, де відносна похибка вибухає: `1e-9` проти `2e-9` — це 100% відносної
  різниці й цілковито неістотна абсолютна.
- **`rtol`** масштабується: `12.5` проти `12.500002` — дрібниця на цій величині й катастрофа на
  `1e-9`.

Жодного окремо не досить.

### Скільки накопичується

Кожна операція fp32 додає близько `1.2e-7` відносної похибки. Похибки частково гасяться, тож ланцюг
із N залежних операцій дрейфує десь між `√N·ε` і `N·ε`:

```
один matmul при K = 1024      ~1e-6      тісний допуск доречний
один блок трансформера        ~1e-5
28 блоків наскрізь            ~1e-3…1e-2
логіти                        порівнювати top-1 токен, а не значення   ← критерій MVP
```

Останній рядок і є формулюванням віхи E10: «той самий top-1 токен», а не «ті самі логіти». Argmax
стійкий до чисельного дрейфу так, як самі логіти — ні.

### Чого допуск не вміє

Він не відрізняє «інший порядок підсумовування» від «вага транспонована». І це добра новина:

```
0.83  проти  0.83000004    інший порядок підсумовування
0.83  проти  −4.21         транспонована вага
```

Проміжного майже не буває. Справжні баги не тонкі чисельно — вони тонкі поведінково, коли модель
просто звучить трохи дурнішою.

### Пастка з нескінченностями

Правило допуску **помиляється в обидва боки**:

```
inf проти −inf:  |inf − (−inf)| = inf,  поріг atol + rtol·inf = inf
                 inf ≤ inf → «рівні»                    ✗

inf проти  inf:  |inf − inf| = NaN,  NaN ≤ будь-що = false
                 → «різні»                              ✗
```

Тому `compare_close` розбирається з нескінченностями **до** застосування допуску.

## T2 — `assert_close`

```
tensors differ at index (0, 1, 1) of (1, 2, 4): actual -0.500000, expected 0.500000
  absolute 1.000000, relative 2.000000, tolerance rtol 0.000010 atol 0.000000
  2 of 8 elements differ
```

### Три рішення, які роблять повідомлення корисним

**Найгірший елемент, а не перший.** Перший — випадковість порядку обходу; найгірший — там, де
розходження найструктурніше. Ранжування за перевищенням порогу: `|a−e| − (atol + rtol·|e|)`.

**Лічильник розходжень** каже те, чого не каже позиція — **тип** бага:

| Скільки не збіглось | Що це зазвичай |
|---|---|
| один елемент | помилка індексації |
| половина | маска або широкомовлення |
| усе | транспонований операнд, переплутана вісь |

**Координати, а не плоский індекс.** У `[B,H,T,T]` повідомлення називає батч, голову, запит і ключ —
тобто одразу відрізняє «голова 3 неправильна» від «останній токен неправильний».

Плюс: розбіжність форм повідомляється окремо, без порівняння значень; будь-який NaN не проходить
ніколи (NaN в активації — завжди баг); обидва операнди можуть бути нещільними, бо еталон часто
приходить як в'ю у буфер golden-файлу.

## T3 — формат еталонних файлів

```
offset  розмір      вміст
0       8 байт      magic "VEDATNSR"
8       4 байти     uint32  код dtype (0 = F32)
12      4 байти     uint32  ранг
16      8·rank      uint64  розміри, зовнішній першим
...     4·numel     float32 дані, щільно, row-major
```

| Рішення | Причина |
|---|---|
| магія на початку | обрізаний або сторонній файл має падати гучно, а не давати тензор шуму |
| лише fp32, але поле dtype є | харнес порівнює з обчислювальним типом Veda (AD1); поле існує, щоб **відхилити** чужий файл |
| ранг і розміри до даних | читач знає потрібну довжину тіла й звіряє її з розміром файлу — двобічно |
| лише щільні дані | дамп це **значення**, а не в'ю; страйди у формат не входять |

**Це навмисно не safetensors.** E4 читатиме той формат, і golden-файл, який ділить код із
завантажувачем, що сам перевіряється, — це харнес, здатний погодитися з багом.

Заголовок пишеться по одному полю фіксованої ширини з явним порядком байтів, ніколи не `memcpy`
структури: її вирівнювання — пастка переносимості, яка коштує години.

Круговий обхід порівнюється **точно, без допуску**: це копіювання, а не арифметика. Нещільне в'ю
зберігається в індексному порядку, тож транспонований тензор повертається щільним значенням.

Перевірено шість сценаріїв псування, кожен із шляхом і причиною: відсутній файл, чужа магія, файл
коротший за магію, обрізане тіло, задовге тіло, невідомий dtype.

## T4 — дампер і крос-мовна перевірка

### `tools/veda_tensor.py`

Той самий формат у ~50 рядках чистого `struct`. **Без numpy, без torch.** Існує саме для того, щоб
C++-читач звірявся з **незалежною** реалізацією того самого опису: якщо дві реалізації розходяться,
баг в описі формату, і дізнатися це зараз набагато дешевше, ніж після 600 МБ дампів.

### `tools/dump_reference.py`

Ставить forward-хуки на вкладення, кожен із 28 блоків і фінальну норму, проганяє один фіксований
промпт і пише кожен перехоплений тензор:

```
embeddings.bin              після пошуку вкладень
layer_00_output.bin …       після кожного блоку   ← основа будь-якого бісекшену
final_norm.bin
logits_last.bin             лише остання позиція ([1,T,V] це ~600 МБ)
```

Поблочні виходи — найцінніше: двійковий пошук по 28 файлах знаходить перший шар, що розійшовся, і
далі вже внутрішньошарові дампи кажуть, де саме всередині.

**Детермінізм:** фіксований промпт, `manual_seed`, `eval()`, `inference_mode`, і дамп у **fp32**
незалежно від того, що ваги bf16 — ціль порівняння це обчислювальний тип Veda (AD1).

**Ізоляція.** Скрипт живе в `tools/`, не в `src/`. Жоден таргет CMake його не згадує — і це
перевіряється тестом, а не обіцянкою. Файли дампів не комітяться: вони сотні мегабайтів, скрипт їх
перегенеровує.

### Перевірка через межу мов

`tests/cross_language_roundtrip.py` ганяє формат **в обидва боки**: C++ пише — Python читає, Python
пише — C++ читає, і файли звіряються побайтово. Односторонньої перевірки було б замало: хибно
прочитаний опис формату чудово переживає власний круговий обхід і при цьому дає файли, яких жоден
еталонний дампер не напише.

Тест підключений до `ctest` через `find_package(Python3)`; якщо інтерпретатора немає — він просто
не додається, бо збірка Veda не має від Python залежати.

**Знахідка на цьому кроці:** у Python числа це double, тож `-0.1` там **не те саме число**, що
`-0.1f` у файлі. Фікстура прогоняється через `struct.pack/unpack` у fp32 перед порівнянням — це не
допуск, а те саме значення, записане в тій точності, яку файл насправді зберігає. Тест перевіряє й
саму цю відмінність окремим рядком.
