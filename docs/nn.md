# NN Primitives (епік E6) — що реалізовано

Документ описує `veda::nn` — перший модуль, чиї об'єкти **володіють вагами**. Стан: **епік E6
завершено** (сторі S1–S3, таски T1–T5; документи задач — у
`_bmad-output/planning-artifacts/roadmap/tasks/E6-*`).

Сусідні шари: [`tensor.md`](tensor.md), [`ops.md`](ops.md), [`io.md`](io.md),
[`harness.md`](harness.md), про увагу — [`attention.md`](attention.md), про токенізатор — [`tokenizer.md`](tokenizer.md), про генерацію — [`generate.md`](generate.md), про продуктивність — [`performance.md`](performance.md).

**Головна ідея епіку:** операція — це чиста функція, шар — це те, що тримає навчені параметри
(архітектура §2). RMSNorm — найяскравіший випадок: математика в `ops::rms_normalize` (E2), γ-обгортка
тут. Саме цей поділ дозволив перевірити нормалізацію на числах, порахованих на папері, за два епіки
до того, як з'явився перший файл моделі.

## Стан за тасками

| Таска | Тип | Що дає | Стан |
|---|---|---|---|
| E6.S1.T1 id — це номер рядка | Learn | вкладення як пошук, межа операція/шар | ✅ |
| E6.S1.T2 `nn::Embedding` | Build | `[B,T]` → `[B,T,D]`, правило AD2 | ✅ |
| E6.S2.T3 що робить проєкція | Learn | геометрія, розкладка `[out, in]`, де параметри | ✅ |
| E6.S2.T4 `nn::Linear` | Build | проєкція через `matmul_nt`, необов'язковий зсув | ✅ |
| E6.S3.T5 `nn::RMSNorm` | Build | операція плюс навчений γ | ✅ |

**Віха епіку досягнута:** id токенів можна вкласти, спроєктувати й унормувати через справжні
об'єкти-шари.

**Критерії прийняття виконано:** жоден шар не алокує власних ваг — усі приходять як в'ю тензорів
(AD2); кожен шар конструюється синтетичними вагами, і всі тести саме так і роблять.

## Публічний інтерфейс

```cpp
namespace veda::nn {

class Embedding {
    explicit Embedding(core::Tensor table);                     // [V, D]
    core::Tensor forward(const std::vector<int64_t>& ids,
                         const core::Shape& id_shape) const;    // [B,T] -> [B,T,D]
    size_t vocab_size() const;  size_t hidden_size() const;
};

class Linear {
    explicit Linear(core::Tensor weight);                       // [out, in]
    Linear(core::Tensor weight, core::Tensor bias);             // bias [out]
    core::Tensor forward(const core::Tensor& x) const;          // [..., in] -> [..., out]
    size_t in_features() const;  size_t out_features() const;  bool has_bias() const;
};

class RMSNorm {
    RMSNorm(core::Tensor gamma, float eps);                     // gamma [D]
    core::Tensor forward(const core::Tensor& x) const;          // [..., D] -> [..., D]
    size_t hidden_size() const;  float eps() const;
};

}
```

Файли: `src/libs/nn/Embedding.h/.cpp`, `Linear.h/.cpp`, `RMSNorm.h/.cpp`.
Тести: `EmbeddingIdeaTest` (T1), `EmbeddingTest` (T2), `ProjectionIdeaTest` (T3), `LinearTest` (T4),
`RMSNormLayerTest` (T5).

## Правило володіння (AD2)

**Жоден шар не алокує власних ваг.** Вони приходять як в'ю в той єдиний буфер, що його створив
завантажувач (E4), тож 622-мегабайтна таблиця вкладень існує рівно один раз, скільки б об'єктів на
неї не посилалося.

Це перевіряється, а не декларується:

```cpp
CHECK(embedding.table().storage() == weights.storage());
CHECK_EQ(weights.storage().use_count(), long{2});   // два власники, не два буфери
```

Наслідок, який робить увесь епік тестованим: **кожен шар конструюється синтетичними вагами.**
Таблиця 4×3, набрана вручну, є повноцінним `Embedding` — без файлу, без завантажувача, без моделі.

## T1–T2 — `Embedding`

**Вкладення — це копіювання рядка, а не обчислення.** Підручникове означення (множення на one-hot
вектор) — та сама функція, і тест це доводить для кожного id. Ціна еквівалентності на реальному
масштабі:

```
one-hot:  151936 × 1024 = 155 582 464 множень, з них 155 581 440 — на нуль
пошук:    1024 копіювання
```

Різниця у 151 936 разів. Математично тотожні; реалізацією є лише одна.

### Три рішення

**Вихід свіжий, а не gather-в'ю зі страйдом 0.** Спокуса є, але повторювані id стали б **аліасами**
одного рядка, і перший же запис зіпсував би обидві позиції. Тест пише в першу копію й перевіряє, що
решта ціла.

**Таблиця читається через страйди** — у тесті вона транспонована й працює. Ніщо в `nn` не сміє
припускати розкладку, якої `io` не обіцяв.

**Форма id передається явно**, не виводиться як `[1, T]`: вимір `B` існує в кожній формі Veda й на
практиці завжди 1 (AD3), і місце, де це тримається чесно, — саме тут.

Id за межами словника кидає виняток із номером: це не дикий вказівник, а розходження токенізатора з
моделлю — конкретний ризик R2 роадмапу.

```
nn::Embedding: token id 7 is outside a vocabulary of 4
```

## T3–T4 — `Linear`

```
y = x · Wᵀ (+ b)        вага [out, in], як вона лежить у файлі
```

Кожен рядок ваги — це **навчене питання** до входу, а елемент виходу — відповідь: наскільки вектор
спрямований уздовж цього напрямку.

### Де насправді параметри

```
на блок:  q [2048,1024] 2.10M   gate [3072,1024] 3.15M
          k [1024,1024] 1.05M   up   [3072,1024] 3.15M      ← GQA: k і v удвічі менші за q
          v [1024,1024] 1.05M   down [1024,3072] 3.15M
          o [1024,2048] 2.10M
                                             ------
                                             15.73M на блок
× 28 блоків                                  440.4M
вкладення [151936,1024]                      155.6M   (вони ж LM-head)
                                             ------
                                             ~596M  ←  ось звідки «0.6B»
```

**FFN тримає ~60% параметрів**, тоді як attention тримає всю концептуальну вагу. **Норми невидимі:**
57 векторів по 1024 float — 0.01% моделі.

### Прохід уперед — один рядок

```cpp
Tensor y = ops::matmul_nt(x, weight_);
return bias_ ? ops::add(y, *bias_) : y;
```

Якби тут був цикл — щось пішло не так. `matmul_nt` несе розкладку AD4 й ітерує батчеві виміри, `add`
широкомовить `[out]`-зсув. Одна річ в одному місці означає, що багу з розкладкою немає де сховатися.

**Тотожність AD4 перевіряється й на рівні шару:** `Linear(w).forward(x)` точно дорівнює
`matmul(x, w.transpose(0,1))` на випадкових входах чотирьох різних форм.

**Зсув — `std::optional`, а не тензор нулів.** Qwen3 має `attention_bias: false`; тензор нулів
коштував би широкомовленого додавання на 197 викликах на кожен токен задарма.

## T5 — `nn::RMSNorm`

```cpp
return ops::mul(ops::rms_normalize(x, eps_), gamma_);
```

Квадратного кореня тут немає навмисно: якби був, поділ, якого просить архітектура, протік би.

**Що додає γ.** Гола операція фіксує величину вектора й зберігає напрямок. γ — навчений вектор `[D]`,
який після цього переважує кожен канал: канал із γ = 2 важить удвічі більше для того, хто читає
результат, канал із γ ≈ 0 вимкнено. Оскільки γ застосовується **після** нормалізації, він не може
повернути те компаундування величин, заради усунення якого норма й існує: на вхід до γ завжди
надходить щось із RMS = 1.

**γ — поканальний, ніколи не попозиційний.** Кожен токен послідовності множиться на той самий вектор.

### Перевірка, обіцяна ще в E2.S4.T11

```cpp
RMSNorm(ones, eps).forward(x) == rms_normalize(x, eps)   // точно, елемент в елемент
```

Не приблизно: множення скінченного float на 1.0 точне за IEEE 754, тож якби шар робив щось, крім
масштабування, тест би впав.

### Знахідка: інваріантність до масштабу точна не всюди

Рядки `[3, 4]` і `[6, 8]` математично нормалізуються в те саме — і у fp32 розходяться в останніх
бітах, бо `√12.5` та `√50 / 2` це різні обчислення. Тест порівнює їх із допуском `1e-6`, тоді як
випадок γ = 1 лишається **точним**: множення на 1.0 не вносить нічого, а різні шляхи до кореня
вносять.

Це рівно та відмінність, яку встановлював E3.S1.T1: «однакова математика, інший порядок операцій —
інші останні біти».
