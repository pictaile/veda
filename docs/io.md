# Weight Container I/O (епік E4) — що реалізовано

Документ описує `veda::io` — шар, що читає ваги й конфігурацію моделі, **нічого не знаючи про
трансформери**. Стан: **епік E4 завершено** (сторі S1–S3, таски T1–T6; документи задач — у
`_bmad-output/planning-artifacts/roadmap/tasks/E4-*`).

Сусідні шари: [`tensor.md`](tensor.md), [`ops.md`](ops.md), [`harness.md`](harness.md),
[`nn.md`](nn.md).

**Головна ідея епіку:** контейнер не знає про модель. `io` не знає, що тензор на ім'я
`model.layers.0.self_attn.q_proj.weight` — це проєкція запитів; він видає відображення «ім'я →
тензор» і на цьому зупиняється. Зіставлення імен із шарами — це `binding`, і воно не може існувати,
доки не існують шари (E10).

## T1 — межі підмножини (Learn)

Два файли в проєкті — JSON, і правило «без зовнішніх бібліотек» стосується обох:

```
config.json       гіперпараметри моделі, кількасот байтів
tokenizer.json    словник і список злиттів, близько 7 МБ
```

Загальна JSON-бібліотека — це тисячі рядків. Парсер, що читає рівно те, що є в цих двох файлах, —
кількасот. Різниця не в зекономлених зусиллях, а в **площі, якою не володієш**: кожна підтримана
можливість — це можливість помилитися, і жодна з них ніколи не буде задіяна тими двома файлами, що
мають значення.

### Що свідомо не підтримується (AD5)

| Не підтримується | Чому відкинути безпечно |
|---|---|
| коментарі, висячі коми | це не JSON; тут таке ніщо не генерує |
| дублікати ключів | не трапляються; «останній перемагає» приховав би справжню проблему |
| літерали `NaN`, `Infinity` | не валідний JSON; конфіг із таким — зламаний |
| потокове читання | найбільший файл 7 МБ, комфортно тримається в пам'яті |

### Сурогатні пари

`\uXXXX` — це **кодова одиниця UTF-16**, і символи поза базовою площиною записуються **двома**
такими escape-послідовностями:

```
😀  =  \ud83d + \ude00
codepoint = 0x10000 + (0xD83D − 0xD800)·0x400 + (0xDE00 − 0xDC00) = 0x1F600
```

Розкодувати половини незалежно — отримати два невалідні символи замість одного емодзі. Це
найімовірніше місце тонкого бага в усьому читачі, і виявиться він у E5 як токенізатор, хибний саме
на тих входах, які покривають тести з кирилицею та емодзі.

Межі UTF-8 перевірені окремо: `0x7F`→1 байт, `0x80`→2, `0x7FF`→2, `0x800`→3, `0xFFFF`→3,
`0x10000`→4. Кирилиця — двобайтова, і саме тому байтовий рівень токенізації поводиться з нею зовсім
інакше, ніж із латиницею (ризик R2).

## T2 — JSON-читач

```cpp
JsonValue config = parse_json(text);

config["hidden_size"].as_int()             // 1024
config["rms_norm_eps"].as_double()         // 1e-06
config["tie_word_embeddings"].as_bool()    // true
config["architectures"][0].as_string()     // "Qwen3ForCausalLM"
config["unused"].is_null()                 // true
config.contains("rope_scaling")            // false
```

### Один буфер, один курсор

Парсер тримає весь текст і позицію. Кожна функція просуває курсор і повертає значення; **жодна не
копіює вхід**. Саме це тримає 7-мегабайтний файл лінійним — підрядок-на-токен є класичною випадковою
квадратичністю. Порядок величини на реальному файлі: ~300 тис. токенів × ~3.5 МБ середнього
підрядка проти одного проходу — це чотири порядки.

Граматика лягає в шість взаємно рекурсивних функцій, по одній на продукцію. Пробіли пропускаються
перед кожним токеном і більше ніде.

### Позиція в кожній помилці

```
json: expected ':' at line 3, column 8
json: trailing content after the document at line 1, column 10
json: nesting deeper than 256 at line 1, column 257
json: high surrogate without a following \u escape at line 1, column 12
```

«Parse error» на 7-мегабайтному файлі майже даремний. Позиція рахується **лише в момент кидання
винятку**, з офсету — тож відстеження рядка й колонки не коштує нічого на кожному символі.

### `as_int` не обрізає

Число зберігається як `double`, а цілочисельність перевіряє аксесор:

```cpp
config["rms_norm_eps"].as_int()   // кидає: 1e-06 не ціле
config["rope_theta"].as_int()     // 1000000 — воно ціле, хоч і записане як 1000000.0
```

Попросити `rms_norm_eps` цілим — це баг у викликачі, і мовчазне обрізання його б заховало.

### Обмеження глибини

Ворожий файл із десяти тисяч вкладених масивів переповнив би стек. Ліміт — 256 рівнів; це на порядки
більше, ніж треба обом реальним файлам, і тепер рішення ухвалює парсер, а не стек.

### Відхилення від ескізу задачі

У документі задачі був `const std::vector<std::string>& keys() const`. Замість нього основний
аксесор — `members()`, що повертає пари «ключ → значення» в порядку документа, а `keys()` лишився
допоміжним і повертає копію. Причина: обхід 150-тисячного словника `tokenizer.json` не має
дублювати кожен ключ у другому векторі.

### Що перевірено

Реальний `config.json` із усіма полями; шість типів значень із довільним вкладенням; числа в усіх
формах, які трапляються (`0`, `-1`, `1e-06`, `1000000.0`, `-2.5e3`, `1E3`); escape-послідовності
разом із кирилицею, CJK та сурогатною парою; сира багатобайтова UTF-8 без escape (`"сон"` і `" сон"`
дають різну довжину — та сама відмінність, на якій тримається E5); чотирнадцять форм зіпсованого
входу, кожна з рядком і колонкою; сирі керівні символи в рядках; обмеження глибини; і документ на
50 тис. записів, який виявив би квадратичність (усі 100 перевірок разом — 0.05 с).

## T3 — формат safetensors (Learn)

```
8 байт      uint64, little-endian: довжина заголовка N
N байт      JSON-об'єкт: ім'я → {dtype, shape, data_offsets}
решта       сирі байти тензорів, щільно
```

Заголовок — це JSON-документ, і саме тому сторі S1 йшла першою.

### Навіщо формат існує

Його попередник — PyTorch `.pt`, тобто Python pickle, — **виконує код** під час завантаження.
Скачати модель означало буквально запустити чужу програму. safetensors існує тому, що галузь визнала
це неприйнятним, і весь дизайн випливає з «файл — це дані, ніколи не інструкції».

### Чотири речі, які легко зрозуміти хибно

- **`data_offsets` відлічуються від початку секції даних**, а не файлу. Абсолютна позиція —
  `8 + N + offset`. Помилка тут читає правдоподібне сміття з середини іншого тензора.
- **Діапазон напіввідкритий `[begin, end)`**, тож довжина — `end − begin`, і вона мусить збігтися з
  тим, що дають форма й dtype. Заради цієї перевірки в E1.S3.T9 і будувався `byte_length`.
- **`__metadata__` — зарезервований ключ** зі строковою мапою, а не тензором. Читач, що цього не
  знає, спробує розібрати `"pt"` як dtype.
- **У файлі немає нічого виконуваного.**

### Шість перевірок, кожна проти читання за межі буфера

1. файл має принаймні 8 байтів;
2. `8 + N` не перевищує розмір файлу;
3. заголовок розбирається як JSON;
4. dtype підтримуваний — невідомий падає гучно, ніколи не переінтерпретується;
5. `end − begin == byte_length(shape, dtype)`;
6. `end` не виходить за секцію даних.

Небезпечний випадок — саме шостий: у файлі, обрізаному посеред тензора, **заголовок лишається
валідним** і чесно заявляє діапазон, якого вже немає.

## T4 — читач

```cpp
const WeightFile weights = read_safetensors("model.safetensors");

weights.tensor_count();      // скільки тензорів
weights.bytes_on_disk();     // скільки прочитано
weights.bytes_resident();    // скільки стало після розширення (AD1)

const Tensor& q = weights["model.layers.0.self_attn.q_proj.weight"];
weights.contains("lm_head.weight");   // false: вкладення зв'язані
```

### Читання потензорно, не файлом цілком

Проковтнути 1.2 ГБ і потім розширити їх у 2.4 ГБ — це 3.6 ГБ у піку без жодної потреби. Читач
переходить до офсету кожного тензора, зчитує тільки його байти в буфер, розширює й рухається далі:
пік — це модель плюс один тензор.

### Складання, а не винахід

Уся сторі спирається на E1: `dtype_from_name` і `byte_length` (T9), `widen_bf16` (T10), перевірений
добуток вимірів у `Shape` (теж T9, який тепер ловить зіпсовану форму із заголовка). Зсуву на 16 біт
тут не написано — він живе в `core`.

### Повідомлення про помилки

```
safetensors "m.safetensors": is 4 bytes, too small to hold a header length
safetensors "m.safetensors": header claims 4096 bytes, the file has 60 after the length prefix
safetensors "m.safetensors": header is not valid JSON: json: expected a value at line 1, column 7
safetensors "m.safetensors": tensor "a": dtype_from_name: unsupported dtype "F16"; ...
safetensors "m.safetensors": tensor "a": claims 16 bytes, shape (2, 2) of BF16 needs 8
safetensors "m.safetensors": tensor "b": ends at 16, past the 10-byte data section
```

### Що перевірено

Усі фікстури зібрані **побайтово вручну** — файл, згенерований тим самим кодом, що його читає, не
доводить нічого. Двотензорний файл (F32 + BF16) читається точно, значення bf16 збігаються з тими, що
встановив E1.S3.T10; `__metadata__` не стає тензором; імена в порядку заголовка, навіть коли офсети
йдуть у зворотному; скаляр і тензор із нульовим виміром; файл без тензорів; дев'ять імен у стилі
справжньої моделі; і десять сценаріїв псування, кожен із назвою файлу й конкретною причиною.

## T5 — що контролює кожне поле (Learn)

| Поле | Символ | Що визначає |
|---|---|---|
| `hidden_size` | D | ширина залишкового потоку — вхід і вихід кожного блоку |
| `intermediate_size` | F | внутрішня ширина FFN |
| `num_hidden_layers` | — | скільки блоків складено |
| `num_attention_heads` | H | скільки голів запитів |
| `num_key_value_heads` | Hkv | скільки голів ключів/значень — менше за H, це і є GQA |
| `head_dim` | Dh | ширина однієї голови |
| `vocab_size` | V | скільки токенів покривають вкладення й LM-head |
| `rms_norm_eps` | ε | захист усередині кореня в кожному RMSNorm |
| `rope_theta` | — | база частотної драбини RoPE |
| `tie_word_embeddings` | — | чи LM-head перевикористовує матрицю вкладень |
| `max_position_embeddings` | — | ліміт контексту й розмір KV-кешу (E12) |

### Dh **заявляється**, а не припускається

Очевидне співвідношення `Dh = D / H` виконується для багатьох моделей — але Qwen3 вказує `head_dim`
у файлі явно, і воно **не зобов'язане** дорівнювати `D / H`. Коли вони розходяться, правий файл, а не
припущення. Тому конфіг читає `head_dim`, якщо він є, і падає на `D / H` лише за його відсутності.

Наслідок для форм: `q_proj` дає `H·Dh`, `k_proj` і `v_proj` дають `Hkv·Dh`, і жодне з них загалом
**не дорівнює D**. Це найімовірніше місце, де можна вшити хибну константу — і саме тому критерій
прийняття E9 та E10 каже «жодна архітектурна константа не зашита в код».

### Два поля, помилку в яких не побачить жодна перевірка форм

- **`rope_theta`** — хибна база обертає на неправильні кути; модель видає плавний текст без відчуття
  порядку слів. Це той самий приклад, яким AD7 обґрунтовує еталонний харнес.
- **`rms_norm_eps`** — надто велике значення тихо стискає активації.

### `tie_word_embeddings: true`

LM-head не має власних ваг: матриця вкладень перевикористовується як вихідна проєкція. Шукати
`lm_head.weight` у файлі марно — його там немає.

## T6 — `ModelConfig`

```cpp
const ModelConfig config = read_model_config("config.json");
config.queries_per_kv_head();     // H / Hkv — розмір групи GQA
```

### Перевірити один раз тут, щоб решта коду могла припускати

```
num_heads % num_kv_heads == 0     групи GQA мусять ділитися націло
num_kv_heads <= num_heads         голів KV не буває більше, ніж голів запитів
все, крім двох float і прапорця   додатні цілі
rms_norm_eps > 0                  нуль дозволив би нульовому вектору поділитися на нуль
```

`H % Hkv == 0`, перевірене при завантаженні, — це причина, чому розширення голів у E8 зможе
**асертити, а не обробляти**. Конфіг із 17 головами запитів на 8 голів KV — не те, що варто обходити.

### Невідомі поля ігноруються

Справжній `config.json` має три десятки полів — налаштування квантизації, ковзне вікно, дефолти
генерації. Veda читає одинадцять. Ігнорування решти — саме те, що дозволяє конфігу з новішого
експорту завантажитись; відмова була б суворістю, яка нічого не купує.

**Відсутнє обов'язкове поле кидає виняток із його назвою.** У `hidden_size` немає значення за
замовчуванням. Необов'язкові — `max_position_embeddings` і `tie_word_embeddings` — мають запасний
варіант, розмірності не мають ніколи.

## Віха епіку: `veda_inspect`

```
$ ./build/veda_inspect <каталог моделі>

ModelConfig
  layers            2
  hidden size   D   64
  query heads   H   4
  kv heads      Hkv 2  (2 queries per kv head)
  head dim      Dh  16
  ...

  model.embed_tokens.weight                           (128, 64)
  model.layers.0.self_attn.q_proj.weight              (64, 64)
  model.layers.0.self_attn.k_proj.weight              (32, 64)
  ...
  model.norm.weight                                   (64)

20 tensors, 208.6 KB on disk, 417.2 KB resident as fp32
```

Інструмент проганяє весь `veda::io` без жодного рядка з `nn` чи `model` — і показує вдвічі більший
обсяг у пам'яті, ніж на диску, тобто ціну AD1 у явному вигляді. На зіпсованому файлі він друкує
причину й повертає код 1.

Перевірено на синтетичній «моделі» у стилі справжньої: 20 тензорів, дві пари проєкцій із
`k_proj`/`v_proj` удвічі вужчими за `q_proj` (це і є GQA), дві норми на шар, фінальна норма — і
жодного `lm_head.weight`, бо вкладення зв'язані.
