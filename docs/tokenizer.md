# BPE Tokenizer (епік E5) — що реалізовано

Документ описує `veda::tokenizer`. Стан: **епік E5 завершено** (сторі S1–S3, таски T1–T5; документи
задач — у `_bmad-output/planning-artifacts/roadmap/tasks/E5-*`).

Сусідні шари: [`tensor.md`](tensor.md), [`ops.md`](ops.md), [`io.md`](io.md), [`nn.md`](nn.md),
[`attention.md`](attention.md), [`harness.md`](harness.md), [`generate.md`](generate.md), [`performance.md`](performance.md).

**Ризик R2 роадмапу:** «токенізатор, що відрізняється від еталонного на одне злиття, псує вивід без
жодної помилки». Немає винятку, немає NaN, немає розбіжності форм — модель просто відповідає на
промпт, якого їй не давали. **Кирилиця робить байтовий фолбек основним шляхом, а не крайнім
випадком.**

## Публічний інтерфейс

```cpp
namespace veda::tokenizer {

std::string bytes_to_token_text(std::string_view bytes);   // байти → текст словника
std::string token_text_to_bytes(std::string_view text);    // і назад

class Vocabulary {
    static Vocabulary from_tokenizer_json(const io::JsonValue&);
    std::optional<int32_t> id_of(const std::string& token_text) const;
    const std::string& text_of(int32_t id) const;
    std::string bytes_of(int32_t id) const;
};

class Merges {
    static Merges from_tokenizer_json(const io::JsonValue&);
    std::optional<size_t> rank(const std::string& left, const std::string& right) const;
};

std::vector<std::string> pre_tokenize(std::string_view text);

class Tokenizer {
    static Tokenizer from_tokenizer_json(const io::JsonValue&);
    std::vector<int32_t> encode(std::string_view text) const;
    std::string decode(const std::vector<int32_t>& ids) const;
    void add_special_token(std::string content, int32_t id);
};

class StreamingDecoder {
    std::string push(int32_t id);   // лише повні символи
    std::string flush();
};

}
```

## S1 — байти, не символи

Словник символів Unicode потребував би ~150 000 записів **до** першого злиття й усе одно падав би на
незнайомому. Словник **байтів** потребує рівно 256 і не може впасти ніколи: будь-який рядок будь-якою
мовою — це послідовність байтів. Невідоме слово розкладається на байти, а не стає `<unk>`.

### Ціна для української

```
"cat"      3 символи → 3 байти          "bear"      → 4
"кіт"      3 символи → 6 байтів         "ведмідь"   → 14
```

**До будь-яких злиттів українське речення вдвічі довше за англійський переклад.** Злиття частину
повертають, але нерівномірно: український промпт коштує більше токенів, ліміт контексту
досягається раніше, генерація повільніша на одиницю змісту.

### Відображення байт → друкована кодова точка

`tokenizer.json` — текстовий файл, а байт `0x20` не має друкованого написання. Тому кожен byte-level
токенізатор від GPT-2 і далі відображає 256 байтів на 256 **друкованих** кодових точок:

```
' '   →  Ġ (U+0120)      'A'   →  A     друкований ASCII не змінюється
'\n'  →  Ċ (U+010A)      0xD1  →  Ñ     уже друкований у Latin-1
                         0x81  →  ģ     а цей ні — зсувається
```

Тому кирилиця у файлі виглядає як латинська абракадабра — і **це не мохібейк**, це і є текст токена:

```
"сон"  →  "ÑģÐ¾Ð½"        "кіт"  →  "ÐºÑĸÑĤ"
```

Прочитати `tokenizer.json` і забути перевести назад у байти = токенізатор, що працює англійською й
мовчки псує все інше. Звірено з канонічною таблицею GPT-2; біекція перевірена **вичерпно на всіх
256 байтах** в обидва боки.

### Правило без винятків: жодної нормалізації

Ні lowercase, ні NFC, ні trim. Модель навчена на тих байтах, які їй дали, і будь-яке перетворення
змінює id. Записано правилом у заголовку, бо кожен інстинкт обробки тексту каже протилежне.

## S2 — злиття: BPE це **не** найдовший збіг

Позиція злиття у списку — його **ранг**: перше вивчене було найчастішою парою в корпусі. Кодування
програє тренування заново на конкретному рядку:

```
symbols = по одному на байт
повторювати:
    знайти сусідню пару з найменшим рангом
    злити ВСІ її входження
    поки пари зі злиттям існують
```

### Де вони розходяться

```
словник: "ab", "cd", "abc"      злиття: (a,b)=0  (c,d)=1  (ab,c)=2
вхід "abcd"

найдовший збіг:  "abc" пасує → [abc, d]
BPE:             ab c d → ab cd → стоп → [ab, cd]
```

Два токени в обох випадках, **зовсім різні id**. Жодна сегментація не «неправильна» — правильна лише
та, на якій навчали. Тест стверджує обидві відповіді й окремо перевіряє, що `"abc"` у словнику є і
BPE його не використав.

**Зливаються всі входження виграшної пари одразу**, потім перескан: по одному за раз — інший
алгоритм, який може обрати інше друге злиття.

### Претокенізація

Злиття ніколи не перетинають межу шматка — інакше пари на кшталт `"e t"` у `"the tree"` зливалися б,
і словник заповнився б нісенітницею через пробіли.

```
"the cat"    → ["the", " cat"]        провідний пробіл іде до наступного слова
"2024 рік"   → ["2","0","2","4"," рік"]   цифри поодинці
"Привіт!"    → ["Привіт", "!"]
"a\n\nb"     → ["a", "\n\n", "b"]
```

**Записане обмеження:** еталонне правило — регулярка з властивостями Unicode (`\p{L}`), а
`std::regex` їх не має. Реалізовано ту саму структуру з байтовою класифікацією: **будь-який байт
≥ 0x80 рахується літерою**. Це трактує емодзі й символи як літери, тоді як еталон відносить їх до
«іншого». Для прози латиницею чи кирилицею збігається; довести збіг узагалі може лише порівняння з
еталонним токенізатором на корпусі. Обмеження записане й у коді, і в документі задачі — щоб майбутня
розбіжність мала з чого починатись.

Властивість без утрат перевірена на дванадцяти рядках: шматки конкатенуються назад у вхід **точно**.

## S3 — декодування й спецтокени

### Токен може розкодуватись у пів-символу

Кирилична літера — два байти, емодзі — чотири, і ніщо не заважає злиттю закінчитись між ними. Тому
потоковий декодер тримає незавершений хвіст і віддає лише повне:

```
D1        → ""      (ведучий байт двобайтового символу, чекаємо)
D1 81 D0  → "с"     (один символ готовий, D0 лишається)
D0 BE     → "о"
```

«Повне» визначається структурою самого UTF-8 — ведучий байт каже, скільки продовжень іде далі, тож
обрізаний хвіст упізнається без жодної таблиці. **Максимум три байти утримуються** — це перевірено
як інваріант.

**Перевірка вичерпна:** кожен рядок корпусу розбивається на межі **в кожній позиції**, і після
кожного `push` контролюється, що все віддане назовні — валідний UTF-8, а сума віддань дорівнює
оригіналу. Це критерій прийняття епіку: «streaming decode never emits an invalid UTF-8 byte
sequence».

`flush` віддає залишок **сирим**: часткова послідовність означає, що модель зупинилась посеред
символу, і чесна відповідь — віддати байти, а не вигадати `U+FFFD`, якого модель не породжувала.

### Спецтокени в обхід BPE

`<|endoftext|>` — **один** токен з одним id, і він не має проходити злиття: інакше вийшов би рядок
звичайних токенів, що пишуться так само, а означають для моделі щось інше.

- **кодування:** до будь-якого BPE текст сканується на входження спецтокенів, **найдовший перший**,
  і розбивається навколо них;
- **декодування:** спец-id віддає свій вміст як є, ніколи через байтове відображення.

«Найдовший перший» має значення, коли один спецтокен є префіксом іншого — перевірено тестом.

### Віха епіку

```cpp
decode(encode(s)) == s
```

Для всього корпусу: латиниця, кирилиця, CJK, емодзі, змішане, пунктуація, пробіли, порожній рядок,
`«лапки»`, `ґ`, і те саме зі зареєстрованими спецтокенами. Тримається тому, що обидва напрямки
байт-точні й ніщо не нормалізує — токенізатор, який щось обрізає чи підміняє, падає тут одразу.

## Що лишається недоказаним

Круговий обхід доводить **внутрішню узгодженість**, а не збіг із еталоном. Того, що ід збігаються з
тими, на яких навчали модель, не доводить ніщо, крім порівняння з реальним токенізатором на корпусі
— і цей гачок написаний та **скіпає**:

```
SKIPPED: no reference/tokenizer_corpus.txt.
Round trips prove internal consistency; only a comparison against the
real tokenizer proves the ids match what the model was trained on (R2).
```

Найімовірніші місця розбіжності, у порядку ризику: **претокенізація на емодзі та незвичній
пунктуації** (свідоме наближення), потім порядок додавання спецтокенів.
