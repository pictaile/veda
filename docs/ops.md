# Math Ops (епік E2) — що реалізовано

Документ описує шар `veda::ops` — перший модуль над `core`, і перший код у Veda, що **рахує**, а не
описує. Стан: **епік E2 завершено повністю** (сторі S1–S4, таски T1–T12; документи задач — у
`_bmad-output/planning-artifacts/roadmap/tasks/`).

Про шар нижче див. [`tensor.md`](tensor.md), про еталонний харнес — [`harness.md`](harness.md), про читання ваг — [`io.md`](io.md), про шари з вагами — [`nn.md`](nn.md), про увагу — [`attention.md`](attention.md), про токенізатор — [`tokenizer.md`](tokenizer.md), про генерацію — [`generate.md`](generate.md), про продуктивність — [`performance.md`](performance.md), про autograd — [`autograd.md`](autograd.md).

**Головна ідея епіку:** операція — це чиста функція, шар — це те, що володіє вагами. Softmax і SiLU
не володіють нічим, тож вони операції й ніколи не шари. RMSNorm — і те, і те: математика окремо
(`ops::rms_normalize`), γ-обгортка окремо (`nn::RMSNorm`, аж у E6).

---

## Контракт шару

Він встановлюється тут, у найпростіших операціях, і його копіюють усі подальші:

| Правило | Причина |
|---|---|
| операція — **чиста функція**: входи всередину, новий тензор назовні | §2 архітектури; тестується на числах, порахованих вручну |
| **жодної мутації входу**, жодних `add_` «для швидкості» | §7: це саме та форма, яку потребує autograd; ретрофітити пізніше дорого |
| вихід **завжди свіжий і щільний**, якими б не були входи | входи можуть бути в'ю над одним сховищем — або одне над одним |
| форми **асертяться**, а не припускаються | AD6 |
| входи обходяться **через страйди** | після E1 вони рідко щільні: транспоновані оцінки, зрізаний префікс KV, broadcast-зсув |

## T1 — Broadcasting (Learn)

### Правило

Вирівнюємо форми **справа**. Для кожної пари вимірів:

- рівні — беремо їх;
- одна з них 1 — беремо іншу, сторона з одиницею повторюється;
- інакше — форми не поєднуються, операція мусить відмовити.

Відсутній вимір ліворуч рахується за 1. Результат має ранг довшої форми й у кожній позиції — більший
із двох розмірів.

```
    [B, T, D]        (1, 8, 64)
    [   T, 1]   →    (   8,  1)
    ---------        ----------
    [B, T, D]        (1, 8, 64)
```

### Механізм: страйд нуль

Страйд — це «скільки елементів пропустити, щоб зрушити вісь на одиницю». Постав нуль — і просування
осі не пропускає нічого: кожен індекс уздовж неї читає **той самий** елемент. Повторення без
копіювання, виражене цілком в описі.

```
bias   (3,)    страйди (1,)     буфер: 7 8 9
       broadcast до [2, 3]
       (2, 3)  страйди (0, 1)

at({0,1}) = 0·0 + 1·1 = 1  →  8
at({1,1}) = 1·0 + 1·1 = 1  →  8      той самий елемент, як і задумано
```

Два наслідки:

- **broadcast-в'ю ніколи не щільне**, тому операції мусять ходити входом через страйди;
- **у нього не можна писати** — кілька логічних позицій вказують на один фізичний елемент, запис був
  би неоднозначним. У Veda це не обмеження: операції ніколи не пишуть у свої входи.

### Три місця у forward-проході

```
RMSNorm       [B, T, D] × [B, T, 1]      один масштаб на токен
Linear bias   [B, T, F] + [F]            один зсув на вихідний канал
причальна маска [B, H, T, T] + [T, T]    одна маска на всі батчі й голови
```

Що це коштує без широкомовлення — на прикладі маски при H=16, T=1024:

```
матеріалізація:  16 777 216 float = 64 МБ копіювання на шар, на кожен прохід
broadcast:        1 048 576 float = той самий трикутник, прочитаний 16 разів
```

### Пастка, яку правило уможливлює

```
(T,) = (8,)      per-token вектор
(D,) = (8,)      per-channel вектор, у якого D випадково дорівнює T
```

Обидва — `(8,)`, поєднаються без заперечень і дадуть правдоподібне беззмістовне число. Перевірка форм
ловить **розбіжності** розмірностей, ніколи — їх **сплутування**. Тому архітектура фіксує словник
`B/T/D/H/Hkv/Dh/F/V`, а кожна операція асертить контракт у його термінах.

## T2 — `add`, `mul` і скалярні варіанти

### Як влаштована операція

1. обчислити форму результату за правилом T1;
2. подивитись на обидва входи в цій формі, зі страйдом 0 на кожній повтореній осі;
3. виділити свіжий щільний вихід;
4. пройти вихід в індексному порядку, читаючи обидва входи за тими самими координатами.

Кроки 2 і 4 — це причина, чому E1 йшов першим: `broadcast_to` це `Tensor::view` з побудованими
страйдами, а обхід — формула зсуву. Нової машинерії тут немає взагалі.

Обхід написаний **один раз**, у шаблонному помічнику `zip()`; операції відрізняються лише лямбдою.
Дві рукописні копії вкладених циклів розійшлися б при першій же правці однієї з них.

### Чому вихід мусить бути свіжим

Входи можуть бути в'ю над одним сховищем — або **одне над одним**. `add(x, x)` легальне й мусить
працювати; запис у будь-який із входів зіпсував би обчислення на півдорозі. Тест перевіряє й
хитріший випадок: `add(x, x.transpose(0,1))` — те саме сховище, прочитане за двома різними
правилами.

### Перевірено вручну

```
a = [[1,2],[3,4]]   b = [[10,20],[30,40]]

add(a, b) = [[11,22],[33,44]]        mul(a, b) = [[10,40],[90,160]]
mul([[1,2,3],[4,5,6]], [[10],[20]]) = [[10,20,30],[80,100,120]]
mul(a, 0.5) = [[0.5,1.0],[1.5,2.0]]
add(x, x) == mul(x, 2.0)
```

Плюс: обидва входи після виклику незмінні (перевірено, а не мається на увазі); результат завжди
щільний; нещільні входи (транспоновані, зрізані зі зсувом) дають правильні числа; `(2,3)` проти
`(3,2)` кидає виняток, що називає обидві форми.

### Чому скаляр — окреме перевантаження

Скаляр не має форми. Загорнути його в тензор рангу 0 і поширити — спрацювало б (і такий випадок теж
покритий тестом), але на місці виклику читається погано. Attention хоче сказати рівно це:

```cpp
mul(scores, 1.0f / std::sqrt(dh));
```

### Чого свідомо немає

`sub`, `div`, операції на місці. Нічого з цього Veda поки не потребує, а єдиний імовірний випадок
покривається як `add(a, mul(b, -1.0f))`.

## T3 — що обчислює matmul і чому він коштує стільки (Learn)

```
C[i, j] = Σ  A[i, k] · B[k, j]        k = 0 … K−1

[M, K] × [K, N]  →  [M, N]
     ↑____↑ спільний вимір мусить збігатись і зникає з результату
```

Кожен елемент результату — **один рядок проти одного стовпця**. Множення не комутативне: `A·B` і
`B·A` — різні обчислення, зазвичай навіть різних форм.

### Чому саме ця операція вирішує все

Усе інше у Veda лінійне за кількістю елементів. Matmul — ні: `M·N·K` множень-додавань заради `M·N`
результатів. Подвоєння прихованого розміру **вчетверо** збільшує роботу проєкцій, бо ростуть і M, і K.

Арифметика для Qwen3-0.6B (D=1024, F=3072, Hkv·Dh=512, 28 шарів) — зафіксована тестом:

```
на шар   q+k+v+o      1024·1024 + 1024·512·2 + 1024·1024   ≈  2.6M MAC
         gate+up+down 1024·3072·3                          ≈ 10.0M
                                                      ------------------
                                                      ≈ 12.6M на токен

× 28 шарів                                            ≈ 352M
LM-head  1024 × 151669                                ≈ 155M
                                                      ------------------
                                                      ≈ 0.5G MAC ≈ 1 GFLOP на токен
```

Два наслідки, обидва перевірені як твердження в тесті:

- **LM-head сам по собі — приблизно третина роботи токена.** Тому генерація рахує його лише для
  останньої позиції — тим самим `slice` з E1.S2.T7.
- **Власні добутки attention квадратичні по T, а не по D** (`T·T·Dh` для оцінок і стільки ж для
  контексту). На короткому промпті вони дрібні, на довгому — домінують. Це і є причина, чому KV-кеш
  (E12) настільки змінює відчуття від моделі.

Скалярний C++ дає близько 1 GFLOP/s, тобто приблизно **секунда на токен** — ще до того, як без кешу
префікс переобчислюється на кожному кроці.

## T4 — `matmul`: наївний потрійний цикл

```cpp
float sum = 0.0f;
for (size_t step = 0; step < k; ++step)
    sum += left[row_base + step * a_column] * right[column_base + step * b_shared_stride];
destination[i * n + j] = sum;
```

| Рішення | Причина |
|---|---|
| акумулятор — локальна змінна, не `destination[...]` | накопичувати в пам'яті і повільніше, і гірше читається |
| порядок циклів `i, j, k`, без переставлянь | арифметика однакова для всіх шести порядків; швидкість — це E13, і там спершу міряють |
| зсув рядка A винесений із внутрішніх циклів | не залежить від `j` і від кроку |
| читання **через страйди** | транспоноване в'ю приходить сюди постійно (`Q·Kᵀ`) |
| акумуляція у fp32 | AD1; порядок підсумовування змінює останні біти — тому E3 порівнює з допуском, а не точно |

`K == 0` дає нулі, а не помилку: порожня сума дорівнює 0.

## T5 — `matmul_nt`: варіант із транспонованим B

```
matmul     C[i,j] = Σ A[i,k] · B[k,j]      B це [K, N]
matmul_nt  C[i,j] = Σ A[i,k] · B[j,k]      B це [N, K]
                              ↑ переставлені індекси B — уся різниця
```

### Навіщо він існує

HuggingFace зберігає вагу лінійного шару як `[out_features, in_features]`, тож `Linear` рахує
`y = x·Wᵀ`. Два варіанти: фізично транспонувати кожну вагу при завантаженні, або лишити розкладку й
читати B по рядках.

**AD4 обирає друге.** Транспонувати 2.4 ГБ, щоб не писати одну функцію — хибний обмін, а явне `_nt`
на кожному місці виклику є постійним нагадуванням про конвенцію, яка при помилці **тихо дає сміття**.
Архітектура називає це найпоширенішим тихим багом саморобних рантаймів.

```
Linear      [T, in] × [out, in]   →  [T, out]     розкладка файлу, без змін
q_proj      [8, 1024] × [1024, 1024]
gate_proj   [8, 1024] × [3072, 1024]
Q·Kᵀ        [T, Dh] × [T, Dh]     →  [T, T]       K використовується напряму
```

Останній рядок вартий уваги: `Q·Kᵀ` в attention — це природний виклик `_nt`, бо K зберігається як
`[T, Dh]`, а матриця оцінок хоче рядок проти рядка.

### Спільне ядро

Обидві функції відрізняються лише тим, **який зі страйдів B йде по спільному виміру, а який — по
стовпцях результату**:

```cpp
matmul     product(a, b, b.shape()[1], b.strides()[0], b.strides()[1]);
matmul_nt  product(a, b, b.shape()[0], b.strides()[1], b.strides()[0]);
```

Тому цикл написаний один раз і розійтися не може.

### Тест, заради якого таска існує

```cpp
matmul_nt(A, B) == matmul(A, B.transpose(0, 1))
```

На випадкових значеннях, для семи різних наборів форм. Порівняння **точне**, без допуску: порядок
підсумовування в обох шляхах однаковий, тож результати мусять збігатися до біта. Систематична
помилка в індексі не змогла б вижити випадково.

Окремо перевірено, що `matmul_nt` **відхиляє** розкладку звичайного matmul (`[2,3] × [3,4]`) — інакше
переплутаний виклик мовчки рахував би не те.

## T6 — батчевий matmul

Форма кожного операнда ділиться на дві частини:

```
[B, H, T, Dh]
 └─батч──┘└матриця┘
```

Матричні частини підкоряються правилам T4/T5. Батчеві **широкомовляться за правилом T1** — тому
`[B,H,T,Dh] × [1,1,Dh,T]` легальне й ділить одну матрицю на всі голови без матеріалізації копій.

```
[2, 3, 4] × [1, 4, 5]           →  [2, 3, 5]     одна матриця на обидва батчі
[1,16,8,64] × [1,16,64,8]       →  [1,16,8,8]    16 незалежних добутків
[B, T, D] × [F, D]  (matmul_nt) →  [B, T, F]     вага без батчевих вимірів узагалі
[2, 3, 4] × [3, 4, 5]           →  відмова: батч 2 проти 3
```

Останній із дозволених рядків — це `Linear`: вага має ранг 2 і жодних батчевих осей, тож батчева
частина результату походить цілком від активацій. Широкомовлення обробляє це без окремого випадку.

### Ранг 2 — не окремий шлях

Це вироджений випадок із порожньою батчевою частиною. Одна реалізація обслуговує обидва, і тести
T4/T5 проходять незмінними — саме так це й перевіряється. Дві гілки коду розійшлися б.

Ядро `multiply_into()` тепер приймає готовий приймач і по два страйди на операнд, тож його ділять
`matmul`, `matmul_nt` і кожен батчевий елемент кожного з них.

Батчевий зсув обчислюється один раз на матрицю — через ті самі страйди зі здеградованим нулем, що й
у `broadcast_to`. Індекси батчу не протягуються у внутрішній цикл.

### Знахідка: нульовий вимір проти одиниці

Тест на порожньому батчі впав сегфолтом, і санітайзер показав читання за нульовим вказівником. Причина
була **не в T6, а в `broadcast_shape` з T2**:

```cpp
dims[i] = extent_a > extent_b ? extent_a : extent_b;   // «більший з двох»
broadcast_shape((0), ())  →  max(0, 1) = 1             ✗
```

Вимір нульової довжини проти одиниці має лишатись **нулем**: сторона з одиницею повторюється нуль
разів. Вибір «більшого» натомість заявляв елемент, якого не існує — і батчевий matmul сумлінно
намагався його прочитати з порожнього сховища.

Правильне правило — не максимум, а «сторона з одиницею поступається іншій»:

```cpp
dims[i] = extent_a == 1 ? extent_b : extent_a;
```

Помилка жила з T2 і поелементними операціями не проявлялась: там обидва операнди мали однакову
нульову форму, і результат виходив порожнім у будь-якому разі. Знадобився операнд без батчевих
вимірів, щоб вона вилізла. Перевірки на нульовий вимір додані і в `BroadcastingTest`, і в
`ElementwiseTest`.

Усі тести шару додатково прогнані під `-fsanitize=address,undefined` — чисто.

## T7 — ідея softmax (Learn)

```
softmax(x)ᵢ = exp(xᵢ) / Σⱼ exp(xⱼ)
```

Довільні числа на вході, розподіл на виході: усе додатне, сума рівно 1.

**Чому експонента, а не просто `xᵢ / Σx`.** По-перше, від'ємні входи давали б від'ємні
«ймовірності» й суму, що може бути нулем. По-друге, експонента **розділяє**: вона росте швидко, тож
більший бал отримує непропорційно більшу частку. Це і є «м'який максимум» — жорсткий віддав би все
переможцеві й не був би диференційовним, що фатально при навчанні.

**Тільки різниці мають значення, не пропорції.** `[1,2]` і `[10,20]` дають дуже різні розподіли.

### Зсувна інваріантність

```
softmax(x + c)ᵢ = exp(xᵢ+c) / Σ exp(xⱼ+c) = exp(c)·exp(xᵢ) / (exp(c)·Σ exp(xⱼ)) = softmax(x)ᵢ
```

`exp(c)` скорочується. Це не цікавинка, а **дозвіл** на наступний абзац.

### Чому максимум віднімати обов'язково

`exp` переповнює fp32 одразу після 88:

```
exp(88)   ≈ 1.6e38   ще скінченне
exp(89)   = inf
exp(1000) = inf   →  inf / inf = NaN
```

Бали attention у сотнях — звичайна річ. Тому реалізація завжди рахує

```
m = max(x)
softmax(x)ᵢ = exp(xᵢ − m) / Σ exp(xⱼ − m)
```

За зсувною інваріантністю це **та сама функція**, але найбільший аргумент тепер рівно 0, `exp(0) = 1`,
решта — у проміжку (0, 1]. Переповнення неможливе за побудовою, а знаменник не менший за 1, тож і
ділення на нуль немає.

Зникнення в нуль лишається — `exp(−200)` це 0 — але воно нешкідливе: бал на 200 нижчий за максимум
**і має** бути невідрізненним від нульової ймовірності.

`SoftmaxIdeaTest` тримає обидві версії поруч: наївна на `{1000, 1001}` дає NaN, стабільна — те саме
`[0.269, 0.731]`, що й `softmax([1, 2])`.

## T8 — `softmax` уздовж довільної осі

```cpp
core::Tensor softmax(const core::Tensor& t, size_t dim);
```

Вісь — параметр, а не припущення в циклі: attention бере softmax по останній осі `[B,H,T,T]`,
семплер — по останній осі `[B,V]`.

### Доріжки

**Доріжка** — одновимірний пробіг уздовж `dim` із зафіксованими рештою координат. `[B,H,T,T]` при
`dim = 3` має `B·H·T` доріжок довжиною T. Зовнішній обхід — той самий carry-the-index цикл, що й в
інших операціях, але з пропуском осі softmax; внутрішній іде по ній через її страйд.

Три проходи по доріжці: **максимум → сума → ділення**. Злити їх в один (онлайн-нормалізатор) можна,
і це рівно те, що E13 спершу виміряє, а вже потім робитиме.

Це перша операція з такою структурою — вона повториться в `rms_normalize` (T10) і в `argmax`
жадібного семплера (E11).

### Крайові випадки з правильною відповіддю

| Випадок | Результат | Чому |
|---|---|---|
| довжина осі 1 | рівно `1.0` | `exp(0)/exp(0)`, без похибки |
| довжина осі 0 | порожній тензор тієї ж форми | нічого писати |
| `−inf` у доріжці | рівно `0` на цій позиції | `exp(−inf − m) = 0` — саме заради цього E7 маскує через `−inf` |
| уся доріжка `−inf` | NaN | у повністю замаскованого рядка немає розподілу; причальна маска такого не створює, бо позиція *t* завжди бачить себе |

### Дві деталі реалізації

- **Сума накопичується у `float`, не в `double`.** Ширший акумулятор був би точнішим — і саме тому
  тихо розійшовся б із еталоном, з яким порівнює E3. Veda всюди fp32 (AD1).
- **Порівняння в тестах — із допуском `1e-6`**, на відміну від розширення bf16, яке звірялось точно.
  Тут справжня арифметика, і останні біти залежать від порядку підсумовування.

Перевірено: обидві осі 2×2 (обидва результати «валідні ймовірності», але правильний лише один),
форма attention `[1,2,3,3]` із сумою 1 у кожному рядку кожної голови, причальний рядок із двома
`−inf`, транспонований і зрізаний входи. Тест прогнано під `-fsanitize=address,undefined`.

## T9 — навіщо потрібна нелінійність і що таке гейт (Learn)

**Без нелінійності 28 шарів згортаються в один.** `W₂(W₁x)` дорівнює `(W₂W₁)x` — одна матриця, і вся
глибина не дає нічого. Це перевірено в тесті буквально: `matmul(matmul(x, w1), w2)` збігається з
`matmul(x, matmul(w1, w2))` до біта, а варто вставити `silu` між ними — вже ні.

```
silu(x) = x · σ(x) = x / (1 + exp(−x))
```

Три властивості: `silu(0) = 0`; для великих додатних прямує до `x`; для великих від'ємних плавно
згасає до 0. І **немонотонність** — біля `x ≈ −1.28` вона провалюється нижче нуля, перш ніж зрости.
Ця невелика від'ємна пелюстка навмисна й відрізняє SiLU від згладженого ReLU.

**Гейт.** SwiGLU (E9) розділяє вхід FFN на дві проєкції й перемножує їх:

```
gate = silu(W_gate · x)
up   = W_up · x
out  = W_down · (gate ⊙ up)
```

Активація застосовується лише до **однієї** гілки. Ця гілка вирішує, поканально, скільки іншої
пропустити — навчений поелементний клапан. Ось чому в FFN три матриці, а не дві, а сам момент
гейтування — це звичайний `mul` із S1.

```
gate = silu([2, −2]) = [1.7616, −0.2384]
up   =                 [10, 10]
out  =                 [17.616, −2.384]     ті самі up, зовсім різна доля
```

## T10 — `silu` і `gelu`

```
silu(x) = x / (1 + exp(−x))
gelu(x) = 0.5·x·(1 + tanh(√(2/π)·(x + 0.044715·x³)))
```

**Переповнення без жодної гілки.** При `x = −100` вираз `exp(100)` дає `inf`, а `x/inf` дає `−0` —
що і є правильною відповіддю. Перевірено на `−100`, `−700` і `−1e30`: усе скінченне.

**Яка саме GELU.** Реалізовано наближення через `tanh` — те, що PyTorch називає
`gelu(approximate='tanh')` і проти чого тренувалась більшість опублікованих моделей. Точна форма
через `erf` відрізняється в четвертому знаку. Qwen3 GELU не використовує взагалі; вона тут тому, що
«яка саме GELU» — рівно та недомовлена деталь, яка потім коштує пів дня.

**Вільна перевірка коректності:** оскільки `σ(x) + σ(−x) = 1`, то `silu(x) − silu(−x) = x` за будь-якої
величини. Перевірено на п'яти значеннях.

SwiGLU лишається **двома складеними операціями** — `mul(silu(gate), up)`. Злити їх в одну було б
швидше й приховало б структуру; E13 спершу міряє.

## T11 — RMSNorm проти LayerNorm (Learn)

Без нормалізації величини компаундяться: шар, що збільшує вхід у 1.5 раза, робить це знову на
наступному шарі, і після 28 разів числа далеко за межами діапазону, для якого тренувались ваги.

```
LayerNorm:  out = (x − mean) / √(var + ε)      центрує і масштабує
RMSNorm:    out = x / √(mean(x²) + ε)          лише масштабує
```

Уся різниця — **зникле віднімання середнього**. Це економить прохід по вектору й віднімання на
кожен елемент, а якість для трансформерів не страждає: те перецентрування, якого модель хотіла б,
вона може вивчити сама. Тому всі свіжі відкриті моделі використовують RMSNorm.

**Що зберігається:** напрямок вектора. **Що відкидається:** його величина — після нормалізації
середній квадрат виходу дорівнює 1. Саме величина компаундиться, а напрямок несе зміст.

```
RMSNorm([5,5,5])   = [1, 1, 1]
LayerNorm([5,5,5]) = [0, 0, 0]       ← дві різні функції, різниця не тонка
```

**Чому γ немає в операції.** Шар моделі — це `γ ⊙ rms_normalize(x)`, де γ — навчений вектор `[D]`.
γ це **вага**, а вага робить із цього шар: `nn::RMSNorm` у E6. Операція без ваг перевіряється на
числах, порахованих вручну, без жодного файлу моделі. При γ = 1 шар мусить точно відтворювати голу
операцію — це і буде тест E6.

## T12 — `rms_normalize`

```cpp
core::Tensor rms_normalize(const core::Tensor& t, float eps);
```

Три проходи по доріжці, та сама структура, що в softmax: накопичити квадрати → корінь → поділити.
Механіка доріжок уже була написана, відрізняється лише арифметика.

**Вісь зафіксована, параметра `dim` немає.** Кожне використання в моделі нормалізує прихований
вектор токена по D, а це завжди остання вісь. Параметр був би узагальненням, якого ніхто не просить,
а невірно обрана вісь дає правдоподібні числа, які не ловить жоден тест. Фіксація в сигнатурі прибирає
цей режим відмови.

**ε — параметр, а не константа.** Береться з `config.json` (`rms_norm_eps`, 1e-6 для Qwen3). Жодна
архітектурна константа у Veda не зашита в код — це критерій прийняття E9 і E10.

```
[3, 4], ε=0  →  rms = √12.5 = 3.5355  →  [0.8485, 1.1314],  середній квадрат = 1
[5, 5, 5]    →  [1, 1, 1]
[−2, −2]     →  [−1, −1]              знак виживає, величина ні
[0, 0], ε=1e-6  →  [0, 0]             без NaN
```

Перевірено як властивість: **інваріантність до масштабу** `rms_normalize(k·x) == rms_normalize(x)`
для k від 0.001 до 1e6. Плюс: доріжка довжиною 1 дає ±1, `[B,T,D]` нормалізує кожен токен незалежно,
нещільний і зрізаний входи, ранг 0 кидає виняток.

Тест містить і власну реалізацію LayerNorm — лише щоб контраст був конкретним. У Veda її немає:
Qwen3 її не використовує.
