# Tensor Core (епік E1) — що реалізовано

Документ описує шар `veda::core` після **повністю завершеного епіку E1 (таски T1–T10)** роадмапу
(`_bmad-output/planning-artifacts/roadmap/`).

Про шар вище — математичні операції — див. [`ops.md`](ops.md).

**Головна ідея епіку:** тензор — це *опис* пам'яті, а не сама пам'ять. Storage тримає числа;
shape, strides і offset кажуть, як їх читати. Кожна операція-в'ю (`reshape`, `transpose`, `slice`)
змінює лише опис і не рухає жодного байта. Саме це робить attention доступним за ціною.

## Публічний інтерфейс на сьогодні

```cpp
namespace veda::core {

class Shape {
    Shape();                                   // ранг 0 — скаляр
    explicit Shape(std::vector<size_t> dims);
    Shape(std::initializer_list<size_t> dims);
    size_t rank() const;                       // кількість вимірів
    size_t size() const;                       // добуток вимірів; 1 для рангу 0
    size_t operator[](size_t i) const;         // кидає std::out_of_range
    const std::vector<size_t>& dims() const;
    bool operator==(const Shape&) const;
    std::string to_string() const;             // "(2, 3, 4)"
};

class Storage {                                // некопійований
    explicit Storage(size_t n_elements);       // нулюється
    float* data();
    size_t size() const;                       // в елементах
};

class Tensor {
    explicit Tensor(Shape shape);              // алокує власне сховище
    static Tensor view(std::shared_ptr<Storage>, size_t offset, Shape);
    static Tensor view(std::shared_ptr<Storage>, size_t offset, Shape, std::vector<size_t> strides);

    const Shape& shape() const;
    const std::vector<size_t>& strides() const;
    size_t rank() const;
    size_t numel() const;
    size_t offset() const;                     // в елементах
    const std::shared_ptr<Storage>& storage() const;
    float* data();                             // storage->data() + offset

    float  at(std::initializer_list<size_t> indices) const;
    bool   is_contiguous() const;
    Tensor reshape(const Shape& new_shape) const;          // кидає при незбігу або нещільності
    Tensor transpose(size_t dim_a, size_t dim_b) const;
    Tensor slice(size_t dim, size_t start, size_t count) const;
};

std::vector<size_t> contiguous_strides(const Shape&);
size_t              span_in_elements(const Shape&, const std::vector<size_t>&);

enum class DType { F32, BF16 };                        // тільки на межі з файлом
size_t      dtype_size(DType);                         // байтів на елемент
const char* dtype_name(DType);                         // "F32" / "BF16"
DType       dtype_from_name(std::string_view);         // кидає на будь-що інше
size_t      byte_length(const Shape&, DType);          // очікуваний обсяг у файлі
using ByteBuffer = std::vector<std::byte>;             // куди читає завантажувач до конверсії

constexpr float bf16_to_f32(uint16_t bits);                        // точне розширення
void            widen_bf16(const uint16_t* src, float* dst, size_t n);  // dst алокує викликач

} // namespace veda::core
```

**Жодна з трьох операцій-в'ю не копіює даних.** Усі повертають новий опис над тим самим `Storage`.

## T1 — `Shape`: розмір тензора

Незмінний тип-значення, що перелічує довжини по кожному виміру.

```cpp
Shape s{2, 3};
s.rank();        // 2
s.size();        // 6  — добуток вимірів
s[1];            // 3
to_string(s);    // "(2, 3)"
```

**Рішення і причини:**

- **Окремий тип, не `using Shape = std::vector<size_t>`.** Вектор страйдів — теж «вектор size_t»;
  без окремого типу компілятор мовчки дозволить передати один замість іншого. Це реальна й часта
  помилка.
- **Порожній добуток = 1.** `Shape({}).size() == 1`: скаляр — це один елемент, не нуль. Реалізовано
  через `std::accumulate(..., size_t{1}, std::multiplies{})`, тому поведінка виходить сама собою,
  без окремої гілки. Цикл, що починається з нуля, дав би скаляру нуль байтів.
- **Незмінність.** Розмір рахується один раз у конструкторі й кешується. Форма, що змінилася під
  уже створеним тензором, — окремий клас багів.
- **`operator[]` кидає `std::out_of_range`**, а не асертить: `assert` зникає під `NDEBUG`. У тексті
  помилки є `to_string()` — «...out of range for shape (2, 3)».

**Словник розмірностей** (§5 архітектури), фіксований на весь проєкт: `B` батч, `T` довжина
послідовності, `D` розмір прихованого стану, `H` голови запитів, `Hkv` голови ключів/значень,
`Dh` розмірність голови, `F` внутрішній розмір FFN, `V` розмір словника. Сам `Shape` ніколи не знає,
яка літера за яким виміром — це знання живе в коді, що його будує.

## T2 — `Storage` і `Tensor`: хто володіє пам'яттю

### `Storage`

Плоский одновимірний блок float'ів. Знає лише свій розмір **в елементах**, нічого не знає про форму.

```cpp
Storage(const Storage&) = delete;   // копія 2.4 ГБ ваг має бути помилкою компіляції
```

Буфер нулюється при створенні: неініціалізовані float дають NaN, які тихо проповзають через softmax
і потім важко відстежуються.

### `Tensor`

Три поля, кожне відповідає на одне питання:

```
storage_   shared_ptr<Storage>    ДЕ числа
offset_    size_t (в елементах)   ДЕ починається саме цей тензор
shape_     Shape                  НАСКІЛЬКИ він великий
strides_   vector<size_t>         ЯК його обходити        (додано в T3)
```

Два способи створення розділені навмисно, щоб на місці виклику було видно, що відбувається:

```cpp
Tensor t{Shape({2, 3})};                          // алокує власне сховище — так народжуються активації
Tensor v = Tensor::view(storage, 3, Shape({3}));  // дивиться в чуже — так ваги роздаються шарам
```

**Ключова поведінка:** в'ю — це не знімок.

```cpp
Tensor a = Tensor::view(storage, 0, Shape({2, 3}));   // весь буфер
Tensor b = Tensor::view(storage, 3, Shape({3}));      // другий рядок

b.data()[0] = 99.0f;
a.at({1, 0});   // 99 — запис видно через інше в'ю
```

**`shared_ptr` і час життя.** Кілька тензорів описують одне сховище, і жоден із них не мусить знати,
чи він «оригінал». Буфер живе, поки живий останній тензор — навіть якщо `shared_ptr`, з якого все
почалося, уже знищено (перевірено тестом).

**Offset в елементах, не в байтах.** Усі величини цього шару — offset, страйди, розміри — рахуються
в елементах. Байтова арифметика існує рівно в одному місці: `data()` повертає
`storage_->data() + offset_`. `sizeof(float)` не зустрічається в шарі взагалі. Змішування одиниць
дає off-by-4 помилки, які вилазять лише при ненульовому offset — тобто вже після того, як запрацює
slice, далеко від місця, де їх написали.

**Перевірка меж.** `Tensor::view` відмовляє, якщо в'ю виходить за межі сховища, і кидає
`std::out_of_range` з повною діагностикою (форма, offset, розмір сховища). Перевірка написана в
загальній страйдовій формі (`span_in_elements`), тому не потребуватиме переписування в T5–T7.

## T3 — страйди й `at()`: координати в зсув

Пам'ять одновимірна, тензор — ні. Страйди це те правило, що перетворює одне в інше:

```
offset = Σ  iₖ · sₖ           для k = 0 … n−1
```

де `sₖ` — **скільки елементів пропустити в плоскому буфері, щоб зрушити вимір k на одиницю**.

### `contiguous_strides(shape)`

Для щільного row-major тензора останній вимір упакований з кроком 1, а кожен лівіший переступає
цілий блок усього, що праворуч:

```
sₙ₋₁ = 1
sₖ   = dₖ₊₁ · sₖ₊₁
```

| shape | strides | що означає кожен крок |
|---|---|---|
| `(6)` | `(1)` | 1 елемент на позицію |
| `(2, 3)` | `(3, 1)` | 3 на рядок, 1 на стовпець |
| `(2, 3, 4)` | `(12, 4, 1)` | 12 = ціла пластина 3×4 |
| `(1, 8, 64)` | `(512, 64, 1)` | `[B,T,D]`: один токен = 64 float |
| `()` | `()` | скаляр — порожній вектор страйдів |

Обчислення йде ззаду наперед. Цикл назад по беззнаковому типу — класичне місце помилки
(`k >= 0` для `size_t` ніколи не хибне), тому написано `for (size_t k = rank; k-- > 0;)`.

### `span_in_elements(shape, strides)`

Скільки елементів тензор охоплює від власного початку: `Σ (dₖ−1)·sₖ + 1`, і `0` для тензора з
нульовим виміром. Для щільного дорівнює `shape.size()`, для страйдованого — більше. Використовується
перевіркою меж у `Tensor::view`.

### `Tensor::at({i, j, ...})`

```cpp
size_t flat = offset_;                      // базовий зсув додається ОДИН раз, не до кожного доданку
for (index : indices) flat += index * strides_[k++];
return storage_->data()[flat];
```

Перевірено вручну на буфері `10 20 30 40 50 60` зі страйдами `(3,1)`:
`at({1,2}) = 1·3 + 2·1 = 5 → 60`. Окремо перевірено, що в'ю з `offset = 3` індексується **від свого
нуля**: `second_row.at({0}) == 40`.

**Асерти, не винятки.** За AD6 архітектури: винятки на межах системи (парсинг, завантаження),
`assert` усередині числового шляху. `at()` асертить ранг і межі — гучно під час розробки, відсутнє
в релізній гарячій петлі.

## T4 — контигуальність (Learn)

Тензор **щільний**, коли обхід його елементів у індексному порядку (остання розмірність найшвидша)
проходить буфер наскрізь: без дірок і без стрибків назад.

Перевірка тривіальна: `strides == contiguous_strides(shape)`. Це питання «чи мої страйди ті самі,
які ця форма мала б, якби її щойно виділили».

Той самий буфер `10 20 30 40 50 60`, два описи:

```
shape (2,3), strides (3,1)      обхід: 0 1 2 3 4 5      ← наскрізь, щільний
shape (3,2), strides (1,3)      обхід: 0 3 1 4 2 5      ← стрибає, НЕ щільний (транспонований)
```

Обидва **правильні**. Просто в другому логічний порядок і порядок у пам'яті розійшлися.

### Пастка, заради якої існує таска

`reshape` перетлумачує ті самі елементи під новою формою, читаючи буфер підряд. Reshape
транспонованого в'ю до `(6,)`:

```
що прочитається:   10  20  30  40  50  60     (порядок буфера)
що мало б бути:    10  40  20  50  30  60     (логічний порядок)
```

Дві різні відповіді, **жодна не падає**. У 28-шаровому стеку це вилізе як «трохи не ті числа» без
підказки, де саме. Тому `reshape` мусить перевіряти щільність і відмовляти, а `transpose` — ні:
він нічого не припускає про порядок, лише міняє місцями два числа у формі й ті самі два у страйдах.

### Способи втратити щільність

- **переставлені страйди** — transpose і будь-яка перестановка осей;
- **дірки** — slice, що звужує вимір або бере кожен *n*-й: крок лишається від старої, ширшої
  розкладки. Приклад: `(2,3)` зі страйдами `(6,1)` — останній страйд 1, а щільності немає.

Останній страйд 1 — умова **необхідна, але не достатня**. Форма сама по собі не каже нічого:
`(2,3)` може бути і щільним `(3,1)`, і дірявим `(6,1)`.

`tests/ContiguityTest.cpp` містить функцію `walk()`, що явно рахує послідовність зсувів для будь-якої
пари shape/strides — обидві послідовності вище перевірені, а не «на папері».

## T5 — `reshape`: ті самі елементи, інша форма

```cpp
bool   Tensor::is_contiguous() const;
Tensor Tensor::reshape(const Shape& new_shape) const;   // в'ю, ніколи не копія
```

### `is_contiguous()`

Обхід у індексному порядку має проходити буфер наскрізь. Перевірка йде справа наліво: кожна вісь
мусить переступати цілий блок усього, що праворуч від неї.

**Осі довжини 1 пропускаються** — їхній індекс завжди 0, тобто по них ніколи не крокують, і їхній
страйд нічого не обмежує. Спочатку тут стояло просте порівняння `strides_ == contiguous_strides(shape_)`;
воно виявилось надто строгим — деталі в розділі T7. Скаляр і порожній тензор щільні за визначенням.

### `reshape()`

Операція легальна за двох умов:

1. **кількість елементів не змінилась** — `∏ old == ∏ new`; це перетлумачення, не зміна розміру;
2. **вхід щільний** — інакше індексний порядок і порядок у пам'яті розійшлися (див. T4).

За виконання обох реалізація тривіальна: те саме сховище, той самий offset, нова форма і **свіжі
щільні страйди для неї**:

```cpp
return Tensor(storage_, offset_, new_shape, contiguous_strides(new_shape));
```

Складність не в коді, а в тому, щоб знати, коли відмовити.

```
buffer:  10  20  30  40  50  60

(2,3) → (6,)     6 == 6 ✓, щільний ✓   страйди (1)     читається 10 20 30 40 50 60
(2,3) → (3,2)    6 == 6 ✓, щільний ✓   страйди (2,1)   [[10,20],[30,40],[50,60]]
(2,3) → (4,)     6 != 4                 ✗ відмова
(3,2) зі страйдами (1,3) → (6,)   кількість збігається, щільності немає   ✗ відмова
```

Зверни увагу на другий рядок: нові страйди — `(2,1)`, а **не** старі `(3,1)` і не `(1,3)`. Вони
обчислюються з нової форми з нуля.

### Дві відмови з різними типами й повідомленнями

```
Tensor::reshape (2, 3) -> (4): element count 6 != 4
Tensor::reshape (3, 2) -> (6): tensor is not contiguous (strides (1, 3),
                               contiguous would be (2, 1)); make a contiguous copy first
```

Перша кидає `std::invalid_argument`, друга — `std::logic_error`. Обидві називають обидві форми:
таке повідомлення економить години, коли помилка виникне всередині 28-шарового стеку.

Свідомо **не** реалізовано виведення розмірності через `-1` (як `numpy`/`torch`). Зручно, але ховає
помилки; за потреби додається пізніше.

### Де це реально знадобиться

Розділення на голови в E7 — це саме `reshape`:

```
вихід q_proj      [B, T, H*Dh]    = [1, 8, 1024]
reshape           [B, T, H, Dh]   = [1, 8, 16, 64]     ← ця таска
transpose (T6)    [B, H, T, Dh]   = [1, 16, 8, 64]     ← наступна
```

1024 float одного токена просто читаються як 16 груп по 64. **Копіюється нуль байтів** — у тесті це
перевірено порівнянням вказівників `data()` і спільного `storage()`.

### Побічне доповнення

З'явилось перевантаження `Tensor::view(storage, offset, shape, strides)` — в'ю з довільними
страйдами. Воно потрібне вже зараз, щоб *створити* нещільний тензор для тесту на відмову (у тексті
таски для цього викликається `transpose`, якого ще немає), і буде основою для `transpose` та `slice`
у T6–T7. Стара трипараметрична форма тепер делегує йому, обчисливши щільні страйди.

## T6 — `transpose`: обмін осей через обмін страйдів

```cpp
Tensor Tensor::transpose(size_t dim_a, size_t dim_b) const;   // в'ю, ніколи не копія
```

Транспонування не рухає дані. Воно міняє місцями *значення* двох осей — а оскільки страйд це рівно
«наскільки крокнути, щоб зрушити цю вісь на одиницю», обмін осей і є обміном їхніх страйдів.

```
new_shape[a]   = old_shape[b]        new_shape[b]   = old_shape[a]
new_strides[a] = old_strides[b]      new_strides[b] = old_strides[a]
```

Усе інше — сховище, offset, решта вимірів — без змін. Уся реалізація це чотири присвоєння:

```cpp
std::vector<size_t> dims = shape_.dims();
std::vector<size_t> strides = strides_;
std::swap(dims[dim_a], dims[dim_b]);
std::swap(strides[dim_a], strides[dim_b]);
return Tensor(storage_, offset_, Shape(std::move(dims)), std::move(strides));
```

### Чому це коректно

Через формулу зсуву з T3. Елемент `[i,j]` оригіналу дає `i·s₀ + j·s₁`. Елемент `[j,i]`
транспонованого дає `j·s₁ + i·s₀`. **Та сама сума** — переставлені координати досягають тієї самої
позиції в буфері, а це й є визначення транспонування.

Звідси й відповідь, чому `transpose` працює над будь-яким тензором, а `reshape` ні: transpose нічого
не припускає про порядок, він лише **перейменовує** осі.

```
до:      shape (2,3)  strides (3,1)   [[10,20,30],[40,50,60]]
після:   shape (3,2)  strides (1,3)   [[10,40],[20,50],[30,60]]
буфер:   10  20  30  40  50  60       ← не зрушено жодного байта

перевірка вручну: at({2,1}) = 2·1 + 1·3 = 5  →  buffer[5] = 60 ✓
```

Результат **нещільний**: щільні страйди для форми `(3,2)` були б `(2,1)`, а тут `(1,3)`. Саме як
передбачав T4 — після цієї таски `is_contiguous()` перестає бути формальністю.

### Ланцюжок розділення на голови — тепер повністю

```
вихід q_proj        [B, T, D]       = [1, 8, 1024]    strides (8192, 1024, 1)
reshape (T5)        [B, T, H, Dh]   = [1, 8, 16, 64]  strides (8192, 1024, 64, 1)
transpose(1, 2)     [B, H, T, Dh]   = [1, 16, 8, 64]  strides (8192, 64, 1024, 1)
```

Скопійовано **нуль байтів** на обох кроках — у тесті це перевірено рівністю `data()`. Дані не
зрушились, але індексація тепер відповідає тому, як attention хоче читати: блок `[T, Dh]` кожної
голови адресується як ціле.

Транспонування всередині обчислення оцінок:

```
K                   [B, H, T, Dh]
K.transpose(2, 3)   [B, H, Dh, T]
Q · Kᵀ              [B, H, T, T]
```

### Деталі реалізації

- `transpose(a, a)` легальне й повертає еквівалентний тензор; порядок аргументів не має значення.
- Індекси вимірів асертяться (AD6), тому `transpose(0, 2)` на рангу 2 падає в debug-збірці.
- Загального API перестановки осей (`permute`) свідомо немає: попарний обмін покриває всі потреби
  Veda й композується.
- Працює над уже нещільним входом — перевірено на в'ю з дірками `(2,3)/(6,1)`.

## T7 — `slice`: звуження одного виміру

```cpp
Tensor Tensor::slice(size_t dim, size_t start, size_t count) const;   // в'ю, ніколи не копія
```

Змінюються рівно дві речі:

```
new_shape[dim] = count
new_offset     = old_offset + start · strides[dim]
```

**Страйди не змінюються взагалі.** Це головна ідея: щоб пропустити перші `start` записів уздовж
виміру, треба зрушити точку старту на `start` кроків страйда цього виміру. А всередині зрізу
просування будь-якої осі коштує рівно стільки ж, скільки коштувало — розкладку ж ніхто не змінював,
змінилось лише де починаємо і докуди йдемо.

```
буфер: 10 20 30 40 50 60,  shape (2,3), strides (3,1)

slice(dim=0, start=1, count=1)      slice(dim=1, start=1, count=2)
  shape  (1,3)                        shape  (2,2)
  offset 0 + 1·3 = 3                  offset 0 + 1·1 = 1
  strides (3,1) без змін              strides (3,1) без змін
  читається [[40,50,60]]              читається [[20,30],[50,60]]
  щільний ✓                           НЕ щільний ✗
```

Перевірка `[1,0]` другого зрізу вручну: `offset 1 + 1·3 + 0·1 = 4`, `buffer[4] = 50` ✓.

**Контигуальність.** Зріз по **першому** виміру щільного тензора лишається щільним. Зріз по
будь-якому іншому — загалом ні: між рядками з'являються дірки. У прикладі вище діра — це елемент 40,
який зріз навмисно пропускає.

Кроковий зріз (кожен другий елемент) свідомо **не** реалізовано: Veda його ніде не потребує, а
історію з контигуальністю він ускладнює без вигоди.

### Обидва реальні застосування перевірені тестом

**Останні логіти для генерації.** LM-head видає `[B, T, V]` — передбачення для кожної позиції.
Генерації потрібне лише останнє:

```
logits              [B, T, V]      = [1, 8, 151669]
slice(1, T-1, 1)    [B, 1, V]      = [1, 1, 151669]   offset = (T-1)·V
reshape             [B, V]         = [1, 151669]
```

Без цього довелося б копіювати 151 669 float на кожному кроці генерації — або, гірше, випадково
семплити з не тієї позиції.

**KV-кеш (E12).** Кеш виділяється один раз на повну довжину контексту, валідними є лише перші
`T_so_far` записів:

```
cache               [B, Hkv, T_max, Dh]     виділено один раз
slice(2, 0, t)      [B, Hkv, t, Dh]         валідний префікс, росте щокроку
```

Змінюється **лише одна цифра у формі**. Offset лишається 0, страйди фіксовані, переалокації немає.

### Знахідка: осі довжини 1 і строга перевірка щільності

§5 таски прямо радить: «переконайся через `is_contiguous()`, а не довіряй міркуванню». Тест на
логітах одразу впав:

```
last:                    shape (1, 1, 32)   strides (256, 32, 1)
щільні для цієї форми:                      (32, 32, 1)          → строге порівняння каже «ні»
```

При цьому в пам'яті це **один суцільний пробіг із 32 float**, і reshape до `(1, 32)` абсолютно
безпечний. Причина розбіжності: по осі довжини 1 неможливо крокнути (індекс завжди 0), тому її
страйд ні на що не впливає й не має нічого обмежувати.

`is_contiguous()` переписано на перевірку справа наліво з пропуском осей довжини 1 — та сама
семантика, що в PyTorch. Обидва правила й розбіжність між ними зафіксовані в `ContiguityTest`,
включно з обходом, який доводить, що зсуви йдуть підряд від 0 до 31.

Це той тип помилки, заради якого епік і побудований так: без перевірки reshape зрізаних логітів
кидав би виняток у циклі генерації — тобто в E11, за шість епіків від місця, де насправді сидить
причина.

## T8 — fp32 / fp16 / bf16 (Learn)

Число з рухомою комою — це три поля, упаковані у фіксовану кількість бітів:

```
sign (1 біт) | exponent (масштаб) | mantissa (значущі цифри)

значення ≈ (−1)^sign × 1.mantissa × 2^(exponent − bias)
```

| | всього | sign | exponent | mantissa | діапазон | точність |
|---|---|---|---|---|---|---|
| **fp32** | 32 | 1 | **8** | 23 | величезний | ~7 десяткових цифр |
| **fp16** | 16 | 1 | 5 | 10 | вузький | ~3 цифри |
| **bf16** | 16 | 1 | **8** | 7 | величезний | ~2 цифри |

Ключова колонка — exponent. **bf16 має ту саму 8-бітну експоненту, що й fp32**, тобто покриває той
самий діапазон величин. Відрізняється лише тим, що викидає 16 біт мантиси.

fp16 зробив протилежний обмін: зберіг точність і звузив діапазон. Для нейромереж це виявилось хибним
вибором — на вузькому діапазоні fp16 постійно трапляються переповнення й зникнення в нуль, тоді як
втрата бітів мантиси в bf16 майже не шкодить, бо числа й так зашумлені. Тому сучасні ваги
постачаються в bf16.

### Чому розширення — це зсув

Оскільки поля sign і exponent у bf16 такі самі за розміром і позицією, як у fp32, значення bf16 **є**
старшими 16 бітами відповідного fp32:

```
fp32_bits = bf16_bits << 16
```

Зсув уліво на 16, нулі в молодшій половині. Це вся конверсія. Вона **точна**: кожне значення bf16 має
рівно відповідне fp32, і не втрачається нічого, бо відкинуті біти були відсутні вже до того.

```
1.0f    = 0 01111111 00000000000000000000000 = 0x3F800000
як bf16 = 0 01111111 0000000                 = 0x3F80
назад   = 0x3F80 << 16 = 0x3F800000          = 1.0   ✓

−1.0f   = 0xBF800000   ← відрізняється рівно одним бітом знака
```

Зворотний бік (fp32 → bf16) інформацію втрачає й потребує рішення про округлення. Veda його ніколи
не потребує.

Втрата точності відбувається при **збереженні**, а не при читанні: π = `0x40490FDB` у fp32, як bf16
це `0x4049`, а після розширення — `0x40490000` = 3.140625. Похибка справжня, але внесли її, коли
зберігали ваги. Задача рантайму — бути точним у розширенні.

Спеціальні значення виходять із зсуву самі, без окремої обробки — добра ознака, що підхід правильний:

```
0x0000 → 0x00000000 → 0.0        0x7F80 → +inf
0x8000 → 0x80000000 → −0.0       0xFF80 → −inf
0x7FC0 → 0x7FC00000 → NaN
```

### Ціна рішення AD1

Архітектура матеріалізує ваги у fp32 при завантаженні:

```
Qwen3-0.6B   ~600M параметрів    ~1.2 ГБ як bf16 на диску    ~2.4 ГБ як fp32 у пам'яті
Qwen3-1.7B   ~1.7B параметрів    ~3.4 ГБ на диску            ~6.8 ГБ у пам'яті (треба 16 ГБ)
```

### Що перевірено тестом

`tests/FloatFormatsTest.cpp` не додає робочого коду — він фіксує бітові шаблони, на які спиратиметься
T10: розкладку fp32 на поля, `0x3F80 → 1.0`, `0xBF80 → −1.0`, круговий обхід для дев'яти значень,
втрату точності на π, усі спеціальні значення, і діапазон, недосяжний для fp16.

Окремо перевірено, **що сталося б від помилки на 8 замість 16** у зсуві: результат лишається
скінченним і правдоподібним на вигляд, просто в зовсім іншому порядку величини. Ні падіння, ні
повідомлення — саме той клас тихої помилки, заради якого в E3 будується еталонний харнес.

## T9 — `DType`: що означають байти

```cpp
enum class DType { F32, BF16 };

size_t      dtype_size(DType);                  // 4 і 2
const char* dtype_name(DType);                  // "F32" / "BF16"
DType       dtype_from_name(std::string_view);  // розбір рядка із заголовка
size_t      byte_length(const Shape&, DType);   // очікуваний обсяг тензора у файлі
using ByteBuffer = std::vector<std::byte>;      // сирі байти до конверсії
```

### Навіщо dtype, якщо все рахується у fp32

Бо межа із зовнішнім світом — не fp32. Файл ваг містить bf16, а заголовок safetensors називає тип
рядком. Завантажувач має цей рядок прочитати, знати розмір елемента, щоб знайти протяжність тензора
у файлі, і **відмовити** форматам, яких не вміє.

Це вся область існування `DType` у Veda: **він живе на межі вводу-виводу й ніде більше.** Жодна
операція, жоден шар, жоден фрагмент моделі ніколи не розгалужується за dtype. Саме ця вузькість
рятує від комбінаторного вибуху ядер під кожен тип, заради чого й писався AD1. Якщо колись
всередині операції з'явиться `if (dtype == ...)` — дизайн протік.

Перелік свідомо мінімальний. Додати `F16`, `I8` «на майбутнє» означає додати гілки коду, які ніколи
не виконуються, а тому будуть неправильними тоді, коли вперше знадобляться.

### Перевірка заголовка

```
byte_length = element_count × dtype_size(dtype)
```

Реальний запис із заголовка Qwen3:

```
name    "model.layers.0.input_layernorm.weight"
dtype   "BF16"      shape [1024]      offsets [4096, 6144]

очікується  1024 × 2 = 2048 байт
заявлено    6144 − 4096 = 2048        ✓

зіпсований заголовок [4096, 8192] → заявлено 4096 ≠ 2048 → виняток
```

Без цієї перевірки завантажувач прочитав би 4096 байт у тензор на 1024 елементи й затер би те, що
лежить у пам'яті далі.

`dtype_from_name` — **єдине місце**, де існує відповідність «рядок ↔ enum»; читач заголовка не має
її дублювати. Усе, крім `F32` і `BF16`, падає з винятком, який називає рядок-порушник: тихо
прочитати `F16` як `BF16` означає отримати сміття, схоже на ваги.

```
(1024,)          BF16   →       2048 байт
(1024,)          F32    →       4096 байт
(151669, 1024)   BF16   → 310 618 112 байт
```

Останній рядок — найбільший тензор Qwen3-0.6B. Він же й LM-head: вкладення зв'язані (tied
embeddings), тож ті самі 310 МБ обслуговують обидва кінці моделі.

### Знахідка: переповнення ловилось не там

Перевірка на переповнення спочатку стояла в `byte_length` — і тест на зіпсованому заголовку її
пройшов повз. Причина: множення переповнюється **раніше**, у самому `Shape::size()`.

```
Shape({2^62, 4}).size()   →  2^64  →  загортається в 0
byte_length(...)          →  0 × 4 = 0 байт, жодної помилки
```

Форма з чотирма ексабайтами елементів тихо перетворювалась на порожню, і завантажувач виділив би
нуль байтів під тензор, який заявляє гігабайти.

`Shape::element_count` переписано з `std::accumulate` на перевірений цикл, що кидає
`std::overflow_error` із переліком вимірів. Захист тепер стоїть у першоджерелі — його отримують усі,
хто будує форму з зовнішніх даних, а не лише `byte_length` (де перевірка теж лишилась, бо множення
на розмір елемента може переповнитись окремо).

## T10 — bf16 → fp32: розширення

```cpp
constexpr float bf16_to_f32(uint16_t bits) noexcept;
void widen_bf16(const uint16_t* src, float* dst, size_t n) noexcept;
```

Через цю функцію проходить **кожна вага моделі рівно один раз** — усі 600 мільйонів. Якщо вона
хибна, ніхто не повідомить про помилку: форми правильні, завантажувач успішний, forward-прохід
доходить до кінця й видає токен. Просто щоразу не той. З усього коду Veda це чи не найкоротший і
чи не найвідповідальніший фрагмент.

### Реалізація

```cpp
return std::bit_cast<float>(static_cast<uint32_t>(bits) << 16);
```

Тонкість не в зсуві, а в тому, щоб покласти біти у `float` **без числового перетворення**:

```cpp
uint32_t bits = uint32_t(b) << 16;
float f = bits;              // ХИБНО — конвертує ціле 1065353216 у 1065353216.0f
```

Потрібно **перетлумачити** бітовий шаблон, а не перетворити значення. У C++20+ правильний
інструмент — `std::bit_cast`: constexpr, без порушення строгого аліасингу, компілюється в ніщо.
`union` і `reinterpret_cast` через вказівник формально порушують правила аліасингу навіть там, де
працюють; у C++23 підстав їх брати немає.

Помилка була б на **дев'ять порядків** — і при цьому програма спокійно працювала б далі.

Порядок байтів вирішується завантаженням, яке породило `uint16_t`, а не цією функцією; усі
платформи Veda — little-endian наскрізь, тож обміну не потрібно.

### Жодних спеціальних випадків

Нуль, від'ємний нуль, нескінченності й NaN виходять із зсуву самі. `if` тут означав би, що модель
у голові хибна.

```
0x3F80 → 1.0        0x7F80 → +inf      0x0000 → +0.0
0xBF80 → −1.0       0xFF80 → −inf      0x8000 → −0.0  (знак зберігається)
0x4049 → 3.140625   0x7FC0 → NaN
```

### Що перевірено

- Уся таблиця з таски — через `==`, **без жодних допусків**: розширення точне, а допуск сховав би
  рівно той баг, який тут можливий.
- `static_assert` на трьох константах — функція `constexpr`, тож частину перевірок робить компілятор.
- **Вичерпно: усі 65 536 можливих значень bf16** — для кожного біти результату дорівнюють
  `bits << 16`. Це не вибіркова перевірка, а доведення точності перебором.
- Від'ємний нуль лишається від'ємним (`signbit`), NaN і нескінченності — без окремого коду.
- Пастка як охоронець: `bf16_to_f32(0x3F80) != 1065353216.0f`.
- Масивний шлях: `n == 0` нічого не пише, елемент-вартовий за межами діапазону лишається незайманим.
- Інтеграція: розширення **просто в `Tensor::data()`**, як це робитиме завантажувач у E4 —
  а потім `transpose`, `reshape` і `slice` над цими вагами читають ті самі числа.

### Масштаб

600 мільйонів ітерацій зсуву й запису, один раз на старті:

```
Qwen3-0.6B   ~1.2 ГБ bf16 на вході   →   ~2.4 ГБ fp32 у пам'яті
```

Цикл упирається в пропускну здатність пам'яті. Оптимізувати його зараз не треба — але й випадково
зробити квадратичним (наприклад, розширюючи в `std::vector`, який переалокується) теж. Тому приймач
виділяє викликач, а функція не алокує нічого.

## Тестова інфраструктура

У проєкті не було жодного тесту (`enable_testing()` не викликано). Кожна таска роадмапу має секцію
Tests і вимогу «all unit tests pass» у Definition of Done, тому тестовий таргет був передумовою.

**`tests/TestSupport.h`** — власний харнес, ~130 рядків, без зовнішніх залежностей. GoogleTest
потребує мережі під час конфігурації, а для навчального проєкту «пишемо все з нуля» власний харнес
доречніший.

```cpp
CHECK(cond)
CHECK_EQ(actual, expected)          // друкує обидва значення при розбіжності
CHECK_NE(actual, unexpected)
CHECK_THROWS_AS(expr, exception)
CHECK_ABORTS(expr)                  // ловить спрацьований assert
return VEDA_TEST_SUMMARY("Suite");  // код виходу = кількість провалів
```

`CHECK_ABORTS` існує тому, що `assert` викликає `abort()` і забирає тестовий процес із собою: вираз
виконується у дочірньому процесі через `fork()`, батьківський перевіряє, що той упав із `SIGABRT`.
Під `NDEBUG` макрос стає порожнім.

### CMake

```cmake
enable_testing()

function(veda_add_test name)
    add_executable(${name} tests/${name}.cpp ${ARGN})
    ...
    add_test(NAME ${name} COMMAND ${name})
endfunction()
```

Кожен тест — окремий бінарник із власним `main()`. Додавання тесту — один рядок.

## Рішення, які варто пам'ятати

| Рішення | Причина |
|---|---|
| `Shape` — окремий тип, не `vector<size_t>` | інакше вектор страйдів можна передати замість форми |
| `Storage` некопійований (`= delete`) | випадкова копія 2.4 ГБ ваг має бути помилкою компіляції |
| offset і страйди — **в елементах** | `sizeof(float)` живе рівно в одному місці, `data()` |
| два різні способи створення `Tensor` (конструктор vs `view`) | на місці виклику видно, алокуємо ми чи дивимось у чуже |
| винятки в `view`/`reshape`, `assert` в `at`/`transpose`/`slice` | AD6: гучно на межах, без плюмбінгу в числовому шляху |
| без виведення розмірності `-1` у `reshape` | зручно, але ховає помилки |
| без загального `permute`, без крокового зрізу | попарний обмін і суцільний зріз покривають усі потреби Veda |
| осі довжини 1 не впливають на щільність | інакше зріз останньої позиції логітів хибно вважався б нещільним (див. T7) |
| `DType` лише на межі вводу-виводу | інакше кожна операція обростає гілками під кожен тип (AD1) |
| перевірений добуток у `Shape` | форми будуються з заголовків файлів, які бувають зіпсовані (див. T9) |
| `std::bit_cast`, а не `union`/`reinterpret_cast` | перетлумачення бітів без порушення аліасингу; помилка тут коштує дев'ять порядків |

## Чого ще немає

Епік E1 закрито повністю. Свідомо відсутнє:

| Що | Чому |
|---|---|
| `contiguous()` — матеріалізація щільної копії для відхиленого `reshape` | ще жоден викликач цього не потребував |
| неконстантний `at()`, що повертає посилання | жодна таска E1 його не потребує; запис іде через `data()` |
| `permute`, кроковий зріз, виведення розмірності `-1` | попарний обмін і суцільний зріз покривають усі потреби Veda |
| `F16`, `I8` у `DType` | непротестовані гілки коду будуть хибними тоді, коли вперше знадобляться |
| fp32 → bf16 (звуження) | Veda ніколи не пише ваги |

Далі за роадмапом — **E2 Math Ops**: `add`, `mul`, `matmul` і `matmul_nt`, `softmax`, `silu`,
`gelu`, `rms_normalize`. Усі як чисті функції над цими тензорами, без мутації входу (передумова для
autograd у майбутньому, §7 архітектури).
